# Backend Contract — 项目 Owner

## 目标

建立一套跨语言、跨数据库、跨部署平台的后端工程契约，让人和 Agent 在设计、实现、交付及运行维护后端系统时，能够复用已经验证的工程经验，减少重复犯错。

Contract 必须同时通过三种方式发挥作用：

1. **Gate**：机器能够可靠判断的确定性约束，优先接入已有工具和项目测试。
2. **Agent**：开发过程中的架构、数据、API、安全和可靠性判断约束。
3. **Review**：需要真实运行证据、业务语义或整体取舍的验收与持续巡检。

三种方式互相补充，不要求所有规则都变成 CI 门禁。已知且可稳定复现的错误，应逐步转化为回归测试或其他确定性检查。

## 范围

- 后端架构与模块边界。
- 数据所有权、身份、持久化、事务、迁移与生命周期。
- API、HTTP 语义、认证授权与输入边界。
- 外部依赖、缓存、异步任务、对象存储与资源限制。
- 部署、恢复、日志、指标、追踪及真实用户路径验收。
- Agent 开发约束、工程门禁与事后 Review。

## 非目标

- 不提供新的 Web 框架、ORM、数据库抽象层或通用业务运行时。
- 不强制统一语言、数据库、云平台、目录结构或部署形态。
- 不把 Golf 的项目专属 Owner 约束提升为所有项目的通用规则。
- 不为每条原则开发独立扫描器；优先复用已有工具、测试框架和 CI。
- 不要求缓存、消息队列、微服务、Service Mesh、分布式锁或复杂发布系统成为默认配置。
- 不用没有来源的性能数字、流程锁、审批或版本冻结制造门槛。

## 权威边界

本仓是跨项目后端契约的唯一维护源。消费者项目保留自己的 Owner、业务事实、技术选型和实现；Contract 不取代它们。消费者的真实需求和约束决定某条通用原则的适用方式，不能反向把某个项目的偶然实现升级成全局标准。

## 成功标准

一个现有项目可以低风险增量接入；Agent 能按需读取相关规范；确定性问题由自动检查尽早发现；语义问题由带证据的 Review 识别；已确认的反例能沉淀为回归测试；接入和维护成本不会超过它带来的实际收益。
