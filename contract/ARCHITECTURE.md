# 后端架构与模块边界

## 默认形态

优先从边界清楚的模块化单体开始。只有独立扩缩容、部署、故障隔离、安全边界、团队所有权或运行时限制构成真实需求时，才拆分独立服务。拆分服务会增加网络失败、版本兼容、部署、观测和恢复成本，不能仅以“可扩展性”作为理由。

## 模块职责

- 按业务能力、数据责任和变更原因划分模块。
- 每个持久化实体和写入路径有明确 Owner；其他模块通过明确接口读取或请求变更。
- 依赖方向应可解释。核心业务逻辑不依赖 HTTP、具体数据库驱动或部署平台细节；边界适配器依赖内部业务能力，而不是反向调用。
- API 层负责协议、认证授权、输入输出映射；不承载完整导入流水线、重计算或持久化业务逻辑。
- CLI、定时任务和内部批处理应直接调用正式应用能力，不为内部调用绕行 HTTP API。
- 独立服务必须有独立部署或故障边界的理由、Owner、输入输出契约和运行观测。普通模块不需要伪装成微服务。

## 请求与数据路径

- 浏览器、API、静态文件、对象存储和后台任务应走符合职责的路径。
- 纯转发代理、BFF 或 Gateway 必须有认证、聚合、协议适配、限流等明确职责；没有职责就删除中间层。
- 大对象优先由对象存储/CDN 直接传输；API 负责授权和签发访问能力，不无理由整文件缓冲或流式转发。
- 同一请求应满足一个清晰的消费者任务，避免聊天式细粒度 API 调用和无关数据加载。
- 一个源 snapshot 的昂贵解码或解析应在同一处理边界内复用；不要让多个 producer 各自重复读取、解包和解析。

## 复杂度控制

- 不默认引入缓存、消息队列、事件总线、DAG、分布式锁、Service Mesh 或通用规则引擎。
- 先检查现有模块、数据库约束、平台能力和 CLI 是否已经解决问题。
- 引入代理层、持久队列、物化读模型或额外抽象前，必须说明真实消费者、瓶颈或故障模式，以及维护和恢复成本。
- 目录结构不能代替依赖边界测试；测试必须检查实际 import、写入路径或运行请求路径。

## 验证

可自动验证的依赖方向和禁止依赖进入架构测试；模块职责、服务拆分理由和领域边界由 Agent Review。真实用户路径、请求扇出和对象交付路径需要集成或部署后验证。
