# 后端安全

## 身份与权限

- 认证证明请求者是谁；授权决定请求者能对哪个对象执行什么操作。两者必须分开设计。
- 每个受保护的读写路径都在服务端执行对象级授权，并考虑未登录、本人、他人、不同角色和资源归属变化。
- 写入字段使用明确 Schema 或 allowlist。客户端不能自行提交 Owner、角色、内部状态、稳定身份或审计字段来覆盖服务端事实。
- 前端按钮、隐藏路由、不可猜测 ID 和 CORS 都不能代替服务端授权。

## 输入与资源消耗

- 对路径、Query、请求体、文件类型、文件大小和外部 URL 做校验；校验应与实际业务规则一致。
- 对外部 URL 获取要考虑 SSRF：限制协议、地址范围、重定向和解析后的目标，避免访问本机、内网或云元数据地址。
- 为请求体、上传、并发、执行时间和昂贵操作设置符合业务与平台限制的边界。
- 速率限制用于保护明确的资源或业务操作；不要把它当成身份认证或业务唯一性约束。

## 密钥与运行凭据

- 不把密钥、Token、Cookie、私钥或连接串提交到仓库、测试 fixture 和日志。
- 优先复用平台 Secret 管理与现有 Secret Scanner；扫描结果需要确认是否误报，历史泄漏不能仅靠删除当前文件解决。
- CI 和运行凭据遵循最小权限；代码发布、备份读取、对象发布和清理权限按真实风险分开。
- Workflow 显式声明所需权限，不使用无必要的仓库写权限或长期高权限凭据。

## 响应与日志

- 对外响应不包含堆栈、SQL、内部路径、密钥和不必要的个人数据。
- 日志、trace 和错误上下文不得记录认证凭据或完整敏感请求体；确需关联时使用脱敏标识。
- CORS 只控制浏览器跨源读取，不提供身份验证、对象授权或 CSRF 的完整保护。

## 验证

优先使用成熟 Secret Scanner、依赖漏洞扫描和平台安全功能；项目专属权限矩阵测试必须断言响应和持久化副作用。安全 Review 还应检查真实部署凭据、日志和外部系统，不能仅凭源码扫描宣称安全。
