# 可观测性与运行 Review

## 日志

- 日志描述事件和上下文，使用稳定字段；关键请求、任务和跨服务操作应有可关联的 request / trace / job 标识。
- 区分业务拒绝、输入错误、依赖故障、平台终止和应用异常；不要用一个泛化的 error 或 200 掩盖真实结果。
- 日志不得包含密钥、认证凭据、完整敏感请求体或不必要的个人信息。
- 结构化日志优先复用运行平台和现有日志管道，不为小项目另建观测平台。

## Metrics 与 Traces

- 关键路径关注请求量、延迟分布、错误率、依赖调用、数据库读取、对象存储访问、任务耗时和资源消耗。
- 通过 trace/span 或等效上下文关联一次用户操作跨越的 API、数据库、对象存储和后台任务。
- 指标应能回答实际问题并支持行动；避免只堆无消费者的指标或高基数标签。
- 可先用平台原生指标、日志和 tracing；是否引入 OpenTelemetry Collector、Prometheus 或商业平台按跨平台需求和维护成本决定。

## Health 与用户路径

- Health / readiness / liveness 的语义应明确，不把一个 200 当作系统整体健康。
- 关键路径 Smoke Test 覆盖真实认证态、核心 API、深链接、对象读取和用户可完成的任务；优先只读或隔离环境，避免破坏生产数据。
- 平台强制终止时应用日志可能来不及写出；需要结合平台日志、trace、客户端结果和资源指标判断。
- 没有日志不等于没有失败；日志链路中断本身也是证据缺口。

## 告警与巡检

- 告警应关联用户影响、可行动原因和明确责任人；没有行动价值的噪声告警应调整或删除。
- 开发完成后的增量 Review 关注本次改动和受影响路径；周期 Review 关注趋势、架构腐化、资源增长、故障模式和备份恢复。
- Review 报告明确数据窗口、采样范围、证据来源和未覆盖区域，不将缺失证据写成通过。
