# 后端 Review 与证据采集

## Review 的目的

Review 判断的是系统是否真正解决了消费者问题，而不是仓库里有没有某份规范、测试是否全绿或部署命令是否成功。CLI 只采集证据；Agent 必须结合 Owner、任务意图、真实消费者和运行结果作判断。

## 设计阶段与实现后评审

用户引用 Backend Contract 复查设计时，先使用 [DESIGN-REVIEW.md](DESIGN-REVIEW.md) 按八项原则审查方案与适用专题，提出具体修正。该评审可在没有实现、没有接入 Contract 时进行。以下流程主要用于实现后或现状巡检；不以缺少尚未实现的运行证据否定设计，也不把方案判断冒充运行验证。

## 开始前

1. 阅读消费者项目的 Owner、相关任务意图和本次改动。
2. 确认真实消费者、数据边界、部署目标和影响范围。
3. 阅读相关 Contract 章节与已知反例。
4. 区分本次变更、历史遗留和当前没有证据的事项。

## 先采集，再判断

至少按适用范围检查：

- 代码和模块边界：入口、依赖方向、写入位置、跨模块调用。
- 数据：Schema、migration、唯一约束、身份字段、Owner、外键/Trigger/Procedure/View 的使用理由、引用完整性、重导/重算行为。
- API：OpenAPI、真实路由、权限矩阵、状态码、分页、请求体边界。
- 测试：单元、集成、故障注入、真实 fixture、覆盖范围和未执行项。
- 部署：CI、发布责任、环境配置、资源限制、回滚/前滚方式。
- 对象与文件：发布清单、引用完整性、字节校验、权限和生命周期。
- 运行：日志、trace、查询数量、CPU/内存、外部调用、失败与恢复。
- 产品路径：认证态、关键页面/API、页面默认加载的业务请求次数（超过 3 次复查）、深链接、对象读取和实际业务结果。
- 操作面：真实 CLI 是否覆盖重复操作、常用命令默认值与安全范围；配置分层、合并顺序、必要秘密注入及启动行为。

使用已有工具、平台日志、测试报告和 CLI。Backend Contract CLI 的 review 默认只向终端输出证据；需要留档时显式指定 --out=项目内路径。不要自动把一次性巡检报告写入消费者的 docs/，应遵守消费者 Owner 的文档治理。没有可观测数据时明确记录缺口，不要用推测填补。

## 判断原则

- 一条规则若有确定性证据，应尽可能固化成测试或工具检查。
- Review 发现的问题应说明复现路径、影响、证据、建议和是否改变当前决策。
- 不因理论上仍有不确定性而无限扩大研究；若不同答案不会改变实际决策，停止深挖。
- 不把局部测试通过升级为整体目标完成。
- 不将缺少数据或日志解释为没有问题。
- 不要求每次全仓深度 Review；开发后做受影响范围的增量 Review，周期巡检关注趋势和长期风险。

## 输出格式

每项结论使用以下状态之一：

- 已验证：附实际证据和覆盖范围。
- 已发现问题：附复现方式、影响和建议。
- 未验证：说明缺少什么证据。
- 未运行：列出未执行的检查及原因。
- 不适用：说明项目边界和理由。

报告末尾列出优先处理项、可转化为自动测试的已确认不变量，以及暂时保留为 Agent / Review 判断的事项。不要生成无行动价值的通用风险清单。
