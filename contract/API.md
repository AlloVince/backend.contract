# API 与 HTTP 契约

## API 设计

- 从真实消费者的任务和稳定领域概念设计资源与读模型，不按数据库表逐一暴露。
- API 字段表达稳定业务含义，不泄漏内部表名、producer 名称、对象存储 key、处理顺序或部署实现。
- 优先保持向后兼容。新增可选字段通常不需要机械增加 API 版本；确有破坏性变化时，定义迁移、弃用和消费者切换策略。
- 使用机器可读的 OpenAPI 等契约描述公开接口，并通过工具校验契约文件；再用行为测试验证真实路由、认证、状态码和响应一致。
- 一个页面或业务动作需要的数据应有合适的聚合读模型，避免要求客户端发起大量细碎请求或重复计算稳定汇总。

## HTTP 语义

- GET、HEAD、OPTIONS 等安全方法不得承载业务写入。
- PUT、DELETE 等幂等方法应保持重复调用不会重复产生业务效果；POST 不默认可安全重试。
- 使用准确的 2xx、4xx、5xx 表达结果。资源不存在通常使用 404；合法资源的可选字段为 null 或集合为空，不等同于资源不存在。
- 方法不支持时返回 405 并提供正确 Allow；创建资源时按语义使用 201；无响应体的成功操作可按需使用 204。
- 对外错误响应提供稳定错误类型和可追踪关联 ID，不暴露堆栈、SQL、内部路径或凭据。
- Content-Type、缓存头、重定向状态和 CORS 应符合真实请求语义；CORS 不是身份认证或授权。
- Range / 大文件下载应端到端验证 206、Content-Range、字节长度和 seek；不能只验证 API 返回了下载地址。

## 输入、分页与资源边界

- 对请求体、路径参数、Query、上传文件类型和大小做服务端校验；字段采用明确 Schema/allowlist，禁止 mass assignment 覆盖 Owner、身份或权限字段。
- 对受保护资源执行对象级授权；不能仅验证用户已登录或前端隐藏了按钮。
- 增长型列表必须有界分页、稳定排序和明确非法参数行为；不能先全量读取再在内存切片。
- 请求体、响应体、超时和并发边界依据业务与平台限制确定，不发明跨平台统一数字。
- 避免 N+1 和请求扇出。用真实查询计数、数据库执行计划或集成测试确认数据规模增长时的读取行为。

## 验证

契约 lint 只能证明 OpenAPI 文档符合工具规则；真实行为仍需路由测试。授权需要权限矩阵与数据库副作用断言。性能和查询复杂度需要真实数据规模或可复现 fixture 的证据。
