# 后端 Agent 工作规范

开始后端设计或开发前，先阅读消费者项目自己的 Owner / AGENTS.md，再按任务读取本目录相关规范。至少阅读本文件和 [DESIGN-REVIEW.md](DESIGN-REVIEW.md)；涉及数据、API、安全、发布或运行行为时，继续读取对应专题文件。

新建或实质性修改架构、领域模型、数据库、API、页面业务请求、CLI 或配置前，执行适用的 Design Review。用户要求“用 Backend Contract 复查设计”时，主动按八项原则复查，给出问题、影响与修正后的方案；不要求项目预先接入 Contract，不把设计评审变成审批锁。用户已明确确认的设计原则优先于旧的通用候选实践。

## 通用工作方式

- 先确认真实消费者、业务目标、数据所有权和现有实现，再决定改动；不要只凭技术关键词套模板。
- 优先使用项目已经采用的语言、框架、数据库、CLI、测试和部署方式。没有真实缺口，不引入新框架、服务、队列、缓存、代理层或抽象。
- 模块边界由业务职责、数据所有权和变更原因决定，不按文件类型或每张表机械拆服务。
- API 以稳定领域实体/关系为标准资源边界；跨实体读取采用独立命名且有真实需求的读模型，不直接暴露数据库表、内部 producer、对象存储 key 或实现顺序。
- 明确每项持久化数据的 Owner、稳定身份、唯一性、生命周期和可恢复方式。不要用路径、文件名、日期截断、数组序号或内容哈希猜测业务身份。
- 写操作必须明确原子性和重复执行语义。外部调用设置有界超时；重试只用于可安全重放的操作，且责任集中。
- 服务端执行认证、对象级授权和输入字段校验；前端隐藏按钮不构成权限保护。
- 增长型查询有界并稳定分页；检查数据库真实读取范围，不能全量读取后只在内存切片。
- 对象字节、静态资源、API 计算和后台任务按真实数据路径交付，不让无职责代理或 Worker 承担无谓转发。
- 任何性能数字必须来自用户要求、平台硬限制、SLO 或实测基线；没有依据不发明门槛。
- 缺失值、来源冲突、身份歧义和业务异常应明确暴露；不要静默合并、补零或制造看似正常的结果。

## 三种保障方式

1. **Gate**：能被静态分析、已有工具、测试或平台配置可靠判断的规则，应接入项目现有检查；先复用已有门禁。
2. **Agent**：架构取舍、业务语义、设计和实现选择由 Agent 在开发过程中持续遵循；不能只在最后补一份清单。
3. **Review**：需要运行数据、真实消费者、部署环境或业务常识的判断，必须收集证据并明确结论边界。

不要把 Agent Review 变成一份全仓关键词清单，也不要为了让 Gate 变绿而放宽真实业务测试。已确认的具体不变量可以在 Review 后固化为回归测试。

## 修改与交付

- 修改前先识别相关 Owner、下游消费者、已有测试和历史反例。
- 先修正已有检查器的覆盖缺口，再考虑新增检测器。
- 对新增测试同时验证违规样例会被阻止、合法路径仍可完成。
- 不把单元测试通过等同于端到端或生产验收。
- 交付报告用中文区分：已验证、未验证、未运行、不适用、已知问题；给出实际命令和关键证据。
