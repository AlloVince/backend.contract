# 数据、身份与持久化

## 数据所有权与事实来源

- 每项持久化数据必须有明确 Owner 和允许写入路径。模块或服务可以共享数据库，但不能因此共享所有写权限。
- 区分外部原始事实、规范化/Native 数据、可重建 Derived、产品用户数据、人工修订、审计记录、缓存和临时产物。
- 重新导入或重新计算不得覆盖其他 Owner 的数据；设备事实不能被人工编辑改写，人工 overlay 不能被导入或重算覆盖。
- 数据库表、字段、对象存储和文件的生命周期应反映数据责任。备份、产品对象和临时文件不能共用模糊的删除策略。
- 数据来源和转换过程应能追溯到具体输入与版本，但版本号或 Hash 默认用于记录和复现，不作为阻止正常运行、更新或重建的锁。

## 身份与唯一性

- 先寻找来源系统提供的稳定原生 ID；缺失时才选择稳定且有业务含义的字段组合。
- ID 不应依赖文件路径、显示名、目录结构、扫描顺序、日期截断或数组位置等可变因素。
- 内容哈希可用于识别字节相同、校验完整性或去重输入，不自动等同于业务实体身份。
- 业务唯一性必须落实到持久层约束或原子写入；应用层先查再写无法单独防止并发竞态。
- 同一候选身份对应不同业务事实时，明确报冲突并停止该次合并；不要追加任意字段来“制造唯一”。
- 不足以确定身份时保留歧义并暴露给上层，不静默合并或重复生成实体。

## 事务与并发

- 事务围绕需要同时成立的业务不变量，不包住整个请求生命周期。
- 事务尽量短；不要在持有数据库事务期间等待 HTTP、对象上传、队列或人工操作。
- 并发写入优先使用唯一约束、条件更新和数据库原子能力；只有真实竞争场景无法由这些机制解决时才考虑锁。
- 多表操作必须明确原子性边界。跨数据库、对象存储或第三方服务无法共享事务时，设计可恢复状态、幂等重放或补偿。
- 审计记录与对应业务写入需要按业务要求保持一致；具体实现遵循所用数据库和项目 Owner。

## 查询与 Schema

- 增长型集合必须有明确的默认页大小、最大页大小和稳定排序；具体数值按消费者、数据量和平台约束确定。
- 验证真实 SQL/存储读取范围，避免“全量查询后内存分页”。
- 通过可审计的 migration 演进 Schema；考虑新旧代码短暂共存、迁移重放、失败恢复和必要的回滚/前滚方案。
- 面向用户的业务数据表默认不使用数据库外键；跨独立 Owner、重建或发布生命周期的引用使用稳定 ID，由应用维护完整性。只有几乎不会扩展或独立演进、具备明确收益的封闭关系才考虑外键例外。
- 默认不使用 Trigger / Stored Procedure；业务逻辑、审计或关系维护在应用代码中显式执行，仅在 DESIGN-04 的封闭场景考虑例外；有限使用只读 View。保留必要的主键、唯一约束、NOT NULL、CHECK、索引及事务；具体实现须遵循数据库引擎能力。详见 [DESIGN-REVIEW.md](DESIGN-REVIEW.md) DESIGN-04。
- 迁移不得偷偷承载未声明的生产数据删除或对象存储清理。

## 备份与生命周期

- 备份存在不等于可恢复；按数据重要性验证字节完整性和真实恢复流程。
- 原始备份默认私有，普通产品发布不能顺带删除或公开备份。
- 可重建数据应能从明确的权威输入恢复；缺失时明确失败，不偷偷退回未经授权的冷源或 NAS。
- 临时数据和失败上传应有清理策略；正式数据的保留期与恢复目标由业务风险决定。
