# 数据

新建或实质性修改数据 Schema 时，遵循 [DESIGN-REVIEW.md](DESIGN-REVIEW.md) 的 Schema 设计方法：从真实消费路径反推，用代表性样本主动反证并修正设计。

- 明确数据身份、业务唯一性、事实来源、Owner 和生命周期。优先使用来源提供的稳定业务 ID；不以路径、显示名、顺序或内容 Hash 猜测业务身份。Hash 可用于字节去重和记录版本。
- 唯一性和并发正确性由必要的持久层约束或原子写入保障；冲突和歧义不得静默合并。缺失事实不伪造。
- 不可丢失的数据、可重建产物、人工修订与临时数据分清责任；重导、重算、清理不得破坏其他 Owner 的成果。可重建数据保留必要输入及构建入口，不设版本冻结或 Hash 运行锁。
- 事务围绕真实不变量，保持短小；外部等待不占用长事务。跨系统写入若可能部分失败，按风险提供恢复路径。
- 数据库约束遵循 [DESIGN-REVIEW.md](DESIGN-REVIEW.md) DESIGN-04；不用外键并不取消唯一性、事务和应用侧引用完整性。
- Schema 演进采用与数据价值相称的迁移或重建策略；可重建库优先直接重建。重要持久数据须有可用备份和实际恢复验证；只有在线共存确有需求时才要求兼容迁移。不为可丢弃产物建立备份体系。
- 数据库表与字段的自描述要求遵循 [DESIGN-REVIEW.md](DESIGN-REVIEW.md) DESIGN-09；Comment 是 Schema 的组成部分，应随 Schema 定义和迁移一起维护。
- 数据所有权分区、独立重建与有意识的冗余遵循 [DESIGN-REVIEW.md](DESIGN-REVIEW.md) DESIGN-10；以真实读写和生命周期成本决定规范化程度，而不是追求表数或范式。
