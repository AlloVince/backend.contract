# Architecture & Design Review — 架构与设计评审

本文件是正式 Backend Contract 的设计评审入口，也是 Agent 开展后端架构、领域模型、数据库、API、CLI、配置及涉及后端的页面设计时的前置自检标准。它适用于尚未实现的方案，也适用于已有设计的复查；不要求消费者已安装 Contract。

## 评审方式

- 先理解用户目标，阅读消费者 Owner、已有领域词汇、真实实现与适用的专题规范；新项目没有实现时，使用当前需求和方案，不假装已有运行证据。
- 新建或实质性修改架构、领域模型、数据 Schema、API、页面请求路径、CLI 或配置前，先遵守 DESIGN-00，再按十项设计原则检查相关设计。用户引用 Backend Contract 要求复查设计时，检查全部十项中相关的原则，不强制列出无关项目。
- 本文件源于用户明确确认的设计原则；与早期通用候选实践或正式专题中的宽泛表述有冲突时，以这里的明确设计原则为准。消费者 Owner 的明确项目约束与本规范发生冲突时，指出冲突和影响，不擅自改写 Owner；当前人类明确指令优先。
- 发现问题时给出具体设计修改，优先删掉不必要的概念、依赖、接口或参数。已有兼容性限制须明确处理，不为形式一致破坏既有消费者。
- Review 是常规设计工作，不是额外审批、冻结、流程锁或独立 Agent 调度。简单改动只检查受影响部分，不强行写长报告。

## Schema 设计方法：从真实消费路径反推，并主动反证

适用于关系数据库、JSON Schema、领域数据模型、API 数据结构、导入导出与中间产物。设计者负责发现技术缺口，不把发现缺口的责任转交给产品 Owner。

- **目标与消费者**：先明确真实业务结果、数据由谁生产、由谁消费、如何读写及独立使用。以消费者需要的操作和语义反推字段、粒度、关系及边界，而不是只让生产者方便输出。核对已有实现、Owner 决策、相关历史反例及真实来源结构。
- **样本与初步设计**：优先检查少量具有代表性的真实样本，包括常见情形和足以挑战模型的复杂情形。以真实数据推导必要信息、身份、缺失与歧义的表达、生命周期和权威来源；比较可行替代设计，选择端到端复杂度最低的方案，而不是机械追求范式、嵌套或平铺。
- **模拟真实消费**：用候选 Schema 实际表达样本，沿关键业务路径推演生产、存储、读取、查询、关联、更新、重建与展示中适用的环节。需要独立使用的中间产物应能在缺少后续阶段时被实际消费者使用。检查下游是否不得不猜测、恢复丢失信息、重复解析、补偿或依赖非必要阶段；必要的变换与派生应有明确责任和理由。
- **主动反证并修正**：设计者须主动寻找能使自己方案失败的反例，而不只证明正常样本能通过 Schema 校验。重点检查语义丢失、身份冲突、来源信息不足、生产目标与消费目标错位、生命周期耦合、无法表达的真实关系，以及不必要的依赖和同步成本。发现缺口先修正设计，再用对应样本检验；不要将已知设计问题留给 Owner 发现或让消费者用补丁掩盖。
- **证据与取舍**：按风险用实际样本、查询、最小可运行示例或真实消费结果证明关键设计成立，区分 Schema 表达能力不足、转换实现错误和消费者实现错误。新项目没有真实数据时使用有依据的代表性示例，并明确假设及未验证事项。语法合法、字段齐全、文档自洽或测试全绿都不能单独证明业务适配。

以上是设计工作本身，不是固定步骤审批或机械清单。简单改动只验证相关路径；复杂设计优先用小样本暴露根本问题，必要时才扩大验证。不要求独立 Agent、固定样本数量、额外报告、全量实验或 CI 语义门禁；遵循 DESIGN-00。Owner 负责产品目标与重要取舍，Agent 负责主动推理、反证及修正技术设计。

## DESIGN-00 禁止自锁（最高优先级）

**系统不得以自己设定的流程、状态、版本或保护机制阻止本来合法且必要的工作。** 本原则优先于其他 Contract 默认规则；发生冲突时删除或修改造成自锁的规则、实现和测试，而不是增加审批、解锁流程或豁免登记。

- 默认禁止工作流锁、阶段许可、冻结/解冻、一次性授权、基线登记、强制独立复核、版本或 Hash 匹配前置条件，以及无实际收益的全量预检。状态、版本、Hash、Manifest 用于记录事实和复现，不授予或剥夺正常执行权；输入变化应可正常更新、测试、覆盖或重建。
- 设计者必须证明限制保护的是具体、真实的业务不变量，且没有更简单的方案。优先使用唯一约束、短事务、原子写入、局部隔离、可重试操作。局部故障不得扩大成全局阻塞；派生视图或呈现失败不应撤销已成功的业务提交。
- 仅在真实并发写入、不可丢失数据的原子性、明确安全权限等必要场景保留最小保护。锁必须有明确持有者、范围、有限等待、释放及异常退出恢复路径；未知或过期状态不能永久阻塞。不得因本原则取消真正必要的权限、输入校验、数据约束或正确性测试。
- 遇到现有自锁，不把旧规则、测试或 Agent 自报当作不可改变的事实。在当前用户授权范围内直接修正或删除无价值限制及配套测试；真实失败则修复根因，不盲目放宽。验证合法路径能完成、异常可恢复、无关工作不受影响，而不只验证拒绝路径。

依据：源仓 real-cases/counterexamples.md 的 D/G 历史反例，全局协作案例 N-015、P-003 及 Tokenizer 展示阻断反例。消费者不需要这些历史文件才能执行规则。

## DESIGN-01 实体的提炼（Entity Refinement）

设计首先明确系统中究竟有哪些事物。核心领域概念必须有经过斟酌、区分度高、可长期复用的名称；同一领域内同一概念使用一致词汇，一个名称应足以唤起明确的含义，而不是每次都重复解释。

明确每个关键概念的定义、排除范围、身份、生命周期、Owner、事实来源、关系及允许的操作。区分单体 Entity、Value Object、Relationship、Collection、Read Model / Projection 与传输或持久化结构；不要因为存在一张表或一个名词就创建领域实体。业务概念不应由 ORM、表结构或框架反向决定。

复用项目现有权威词汇；新的重要概念或含义变化记入项目已有领域文档或词汇表，不建立重复词汇体系。不同业务上下文确需同名异义时，明确上下文和映射。

Review 检查：是否能仅凭名称与定义理解实体、边界和关系？是否有重复概念、万能实体、含义漂移或假抽象？

## DESIGN-02 英文命名与单复数

- 单数表达单体或单个实体类型，复数表达同类集合。表名、集合对象、ORM 模型、变量、关系字段和 API 资源的命名应按实际语义清晰区分，并保持可预测映射。例如单体 `work` / `Work`，集合 `works` / `Works`。
- 选择区分度高、指向准确的英文词汇；避免用 `Message`、`Data`、`Info` 等宽泛词汇混装不同事物。若它本身就是明确领域概念，则可以使用。
- 自主选择的领域实体名称，应避免单复数同形或不可数而难以表达单体和集合的词；选择语义准确、单复数可区分的近义词或组合词。允许清晰的不规则复数，不机械要求以 s 结尾。
- 外部协议、已有公共契约或不可替代的标准术语确有约束时，记录例外及如何明确单体/集合，不默默改变含义或为改名破坏兼容性。

Review 检查：名称是否精准且彼此可区分？单体和集合是否一眼可辨？同一概念是否跨层一致？

## DESIGN-03 REST 资源与实体边界

- 标准资源接口默认表达一个领域实体或明确的关系实体的集合或单体。例如 `GET /users` 返回 User 集合，`GET /users/{id}` 返回单个 User，`GET /users/{id}/sessions` 返回受 User 范围约束的 Session 集合。
- 标准实体响应以自身字段为主，可附必要稳定 ID、关系信息、分页元数据及有明确业务理由的有限关联表示。不得因为单个页面方便，随意嵌入其他完整实体、集合或跨实体统计；关联数据需要审查所有权、授权、范围、成本和一致性。
- 真正具有独立、稳定业务语义的跨实体查询，使用明确命名的只读 Query Resource / Read Model，说明组合实体、消费者、数据范围和响应边界。不把页面临时拼装结果伪装为标准实体，也不为了减少请求创建万能 API。
- 普通实体写接口以明确的实体或关系为目标；真实业务动作涉及跨实体写入时，显式表达为领域 Action / Command，说明副作用、授权、原子性、幂等与失败恢复。不得隐藏跨实体级联写入或删除。
- SQL JOIN、View 和内部组合查询不受上述响应边界直接禁止。REST 不是每张表的 CRUD 映射，也不要求把复杂查询与业务命令硬套 CRUD。

Review 检查：能否从资源名、路径和响应判断其实体类型？关联、聚合和副作用是否明确且必要？

## DESIGN-04 数据库约束与独立演进

- 面向用户的业务数据表默认不使用数据库外键；跨独立 Owner、重建或发布生命周期的引用使用稳定普通 ID，由应用维护关系完整性。不要让数据库外键把可独立演进的模块绑定在一起。
- 仅在关系几乎不会扩展或独立演进、属于同一封闭生命周期、外键确有完整性收益且不妨碍迁移时，才考虑外键例外，并说明依据。
- 默认不使用数据库 Trigger 或 Stored Procedure；业务逻辑、审计及关系维护在应用代码中显式执行。只有几乎不需要扩展或独立演进、确有必要的封闭场景才考虑例外，并说明依据。View 可以有限使用，主要用于稳定的只读查询；不得隐藏业务行为或混淆领域实体。
- 不使用外键不等于放弃数据约束。保留必要的主键、唯一约束、NOT NULL、CHECK、索引及事务。应用维护引用时必须明确并发创建/删除、孤儿引用、重建后的重新关联和必要的检查/修复路径；不能依赖简单先查再写来保证并发正确性。
- 评估真实数据库引擎、写入成本、锁、迁移及新旧代码兼容；不假定外键一定性能低，也不假定去掉外键即可解决在线升级。

Review 检查：是否有隐式业务写入、跨生命周期耦合或无明确理由的外键？取消约束后完整性由谁保证？

## DESIGN-05 页面初始加载的业务 API 数量

Web 或 App 页面从打开到所有默认功能加载完成，若需要**超过 3 次页面业务 API 请求，必须进行设计复查**。统计真实请求次数（包括重复请求，而非仅不同 URL）；不计静态资源和跨页面共享的全局初始化接口（如全局用户状态）。由用户随后主动触发的操作另行统计；不能把默认加载延迟执行来规避计数。

设计阶段用预期请求清单与依赖关系检查；实现后按真实浏览器/客户端网络记录验证。超过 3 次时，检查页面职责、领域 API 粒度、请求瀑布、重复读取、缺失的稳定读模型及 N+1。审查响应字节、服务端查询与关键路径成本。

3 是用户指定的设计 Review 触发阈值，不是硬性性能上限。若多次独立请求更符合实体边界、权限、缓存或加载需求，可以保留并解释；不得为了数字破坏 DESIGN-03 或制造超级 API。

## DESIGN-06 人与 Agent 共享正式 CLI

日常运维、状态查询、诊断、数据导入导出、迁移、重建、校验、批处理及恢复等重复操作，原则上都通过人和 Agent 共用的一套正式 CLI 完成。CLI 可薄委托现有 Makefile、包脚本和平台工具，直接复用正式业务能力，不重复实现或绕行无必要的 HTTP。

一次性调查可用临时代码；频繁操作仍需临时写代码或拼 SQL，说明 CLI 规划有缺口，应将可复用能力收敛到正式入口。不是把每一个内部函数都暴露成命令。

CLI 提供可发现的 help、明确错误和退出状态；供自动化消费时提供稳定机器可读输出；长任务提供真实进度、结果和必要的恢复入口。

## DESIGN-07 CLI 参数与默认值

常见操作应以最少必要输入执行。可推导或已有合理默认值的参数不要要求每次重填；默认值及覆盖方式应可通过 help 或配置查明。参数名表达业务语义，避免重复、互斥却没有清楚优先级的选项。

默认行为应安全、可预期；生产目标和高风险写入范围不能因省参数而被危险猜测。破坏性操作保留必要的显式目标及范围，不以额外流程锁替代设计。

## DESIGN-08 分层配置与接近自启动

- 项目提交完整、可读的通用默认配置及开发、测试、生产等环境差异；使用分层合并而非每个环境重复填写全部参数。
- 推荐层次：通用默认 → 环境配置 → 私有/实例覆盖 → 明确声明的环境变量或 Secret 注入。文件名和格式随技术栈决定；部署平台可用其原生配置能力实现相同语义。
- 明确优先级，以及嵌套对象、数组、空值的合并规则，避免无定义的 merge。配置来源应有单一、可解释的最终解析路径。
- `.env` / 环境变量只承载必要秘密、真实部署地址及必须动态注入的值，不把有合理默认值的普通配置大量搬进环境变量。真实秘密不提交、不进入日志；私有覆盖不入库。
- 初始项目应尽量接近自启动；本地开发与测试以安全默认值启动，生产只补真实必要配置。缺少必需凭据或安全配置时明确失败；不能使用不安全的生产默认值来追求开箱可用。
- 提供可读的配置示例、必需项与启动校验；环境之间不得意外共用生产数据或凭据。

## DESIGN-09 数据库自描述与字段注释（Self-Describing Schema）

数据库 Schema 不只是供 ORM 或程序读取的结构定义，也应是可直接检查、可理解的业务资料。开发者查看数据库元数据时，应能理解每张表记录什么、每个字段表达什么，而不必先去其他文档中猜测。

- 每张业务表和每个字段都应提供具体、有信息量的数据库原生 `COMMENT`。表注释说明表所表达的业务对象、记录粒度及必要的归属或生命周期；字段注释说明字段的实际语义，尤其要区分容易混淆的相近字段。
- 根据字段实际情况，在注释中解释单位、格式与精度、时区、枚举值含义、NULL 的业务语义、数据来源、计算/派生方式、快照或当前值等信息。只写“创建时间”“状态”“用户 ID”这类重复字段名、类型或缺乏语义的信息，不算充分注释。
- 注释属于 Schema 的一部分，应与建表定义、迁移或其他权威 Schema 源一起版本管理；字段含义变化时同步更新注释，避免数据库元数据与代码、文档逐渐漂移。数据库引擎支持原生 Comment 时直接使用；不支持时，使用该引擎可持久化、可随 Schema 管理的等价元数据表达，不得无声省略。
- Comment 用于解释语义，不替代类型、NOT NULL、CHECK、唯一约束、索引等真正的数据约束；也不替代领域 Owner 文档。避免把整份设计文档塞进字段注释，保持简洁、准确、可独立理解。

Review 检查：只查看 Schema 和数据库元数据，能否理解表的记录粒度及字段的业务含义？表和字段是否都有准确注释？适用的单位、NULL 语义、枚举、时区、来源及派生规则是否说清？注释是否与真实 Schema 和当前实现一致？

## DESIGN-10 数据所有权分区与有意识的冗余（Data Ownership & Deliberate Redundancy）

数据库设计首先按数据的性质、事实来源、写入所有权、可变性及生命周期划分边界，而不是按页面、CRUD 便利性或机械的数据库范式划分。目标是降低整个系统的复杂度，包括查询、写入、重建、迁移、维护和理解成本。

- 按实际业务识别原始事实、规范化事实、可重建派生数据、用户/人工产生的业务数据、运维元数据等类别；不强制所有项目采用固定分类、颜色或物理数据库数量。每个持久化数据集应有清晰的写入 Owner、权威来源及重建/删除边界；同一表默认不混合独立写入所有权与不同的生命周期，确有简单合理的共存方式时须保证边界可维护。
- 原始事实与人工判断、修订、关联应保持独立。人工变更优先保存实际产生的业务内容、稳定目标 ID 或必要 Patch，通过明确的规则形成有效视图；不要覆盖事实，也不要为了关联而复制整份事实。可重建数据的重新导入、计算、清理不得覆盖或级联删除不可重建的人工成果、其他 Owner 的数据或必要来源备份。跨生命周期引用遵循 DESIGN-04。
- **主动允许适度反范式与冗余，以整体简单性为目标。** 对常用筛选、排序、聚合、关联、显示或独立消费所需的稳定 ID、分类、关键属性、来源元数据和派生摘要，可以有意识地重复保存或预计算。当它能减少不必要的 JOIN、重复解析、跨模块调用、重复计算和复杂查询时，不为了形式上的规范化而强行拆表。也不为了减少 JOIN 一概复制所有数据；按实际访问模式、数据规模和变化频率取舍。
- 每个冗余值都应有唯一明确的权威来源，明确它是当前投影、可重建副本还是有真实业务意义的历史快照；写入或刷新责任、一致性/时效要求及重建方式与收益相称。优先由同一生产流程直接生成或通过简单查询获得；只有实际有收益时才持久化摘要或读模型。不默认引入同步服务、事件总线、版本历史、额外缓存或全量校验机制来维护冗余。冗余不能成为新的独立可编辑事实，也不能侵蚀写入与重建边界。
- 按数据的实际用途选择存储：需要筛选、排序、关联的结构化数据与元数据适合数据库；大对象或主要按整体读取的内容可单独存储并保留引用。不因技术形式不同而制造无意义的中转层；不把独立生命周期的数据强行塞进同一通用模型。

Review 检查：每类数据由谁写、谁读、谁能重建或删除？重新导入和重算是否保留人工成果？必要的冗余是否减少了端到端复杂度，还是转化为更复杂的同步与一致性问题？从真实读写路径检查，不以表数量、JOIN 数量或范式级别作为硬门禁。

## 评审输出与使用

使用者只需要求“用 Backend Contract 复查这个设计”，Agent 应从本文件和相关专题出发检查方案，不要求先运行 CLI，不要求额外提供固定表格。

输出应简洁：总体判断、具体问题与影响、违反的 DESIGN 编号或专题原则、推荐修正后的设计、例外及尚未确定的前提。明确区分方案判断和实现证据；没有实现时不声称测试或运行验证通过。全量设计复查覆盖十项中的适用原则；局部设计按影响范围检查。

实现后按照 [REVIEW.md](REVIEW.md) 用真实 Schema、API、网络请求、CLI、配置及测试验证上述设计。机器可确定性检查的部分复用项目已有工具；语义和取舍由 Agent Review，不创建通用语义硬门禁。
