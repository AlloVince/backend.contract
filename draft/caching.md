# 缓存：逐条评估

> 对应来源：../references/caching.md。主要案例：A-03～A-05、B-01～B-03、C-02、D-06。

| ID | 候选原则 | 第一版结论 | 评估理由与边界 |
| --- | --- | --- | --- |
| CACHE-01 | 先确认真实性能瓶颈再加缓存 | **采用** | 当前事故更多是请求放大、无关加载和查询拓扑错误；缓存会掩盖根因并增加一致性问题。先修查询与 API 设计。 |
| CACHE-02 | 缓存有权威来源，不作为唯一 source of truth | **采用** | 缓存丢失应能从主数据恢复。只有明确设计为持久存储的产品才例外，那时它就不再只是缓存。 |
| CACHE-03 | Cache-aside 明确 miss、读取主存储和回填 | **按需采用** | 这是常见模式但不是唯一模式；只有采用 cache-aside 时才需要规定该流程，不为每个项目强加 Redis 或缓存层。 |
| CACHE-04 | 主数据更新后处理相关缓存失效 | **修改后采用** | 失效、版本化 key、短 TTL 等方式应按一致性要求选择；重点是明确陈旧窗口，而不是一律同步双写缓存。 |
| CACHE-05 | TTL 按业务可容忍陈旧时间设定 | **采用** | 不能凭经验统一设五分钟。不同数据的陈旧风险不同，某些数据甚至不应缓存。 |
| CACHE-06 | 主动失效之外保留 TTL 兜底 | **修改后采用** | 对可能漏发失效事件的缓存有价值；TTL 不能替代正确的失效设计，若数据绝不能陈旧则应选择更强一致性方案。 |
| CACHE-07 | 热 key 过期时按实测决定防 stampede | **按需采用** | 单飞、锁、提前刷新和 jitter 会增加机制。只有热点和并发重建确实造成压力时才引入，避免把锁问题再造出来。 |
| CACHE-08 | 对不存在对象可考虑 negative cache | **按需采用** | 只在重复查询不存在资源形成明显穿透时使用；TTL 要短，且不能让新创建的资源长期表现为不存在。 |
| CACHE-09 | cache key 包含影响结果的版本、租户和权限维度 | **采用** | key 不完整会返回错误或跨用户数据。把权限维度漏掉可能直接成为数据泄漏。 |
| CACHE-10 | 不共享权限不同的用户数据缓存 | **采用** | 安全边界高于命中率；共享缓存必须证明响应确实与用户身份无关。 |
| CACHE-11 | 缓存大对象前评估序列化、网络与内存成本 | **采用** | 缓存命中仍有读出、反序列化和传输成本；大对象可能让缓存比重算更贵。 |
| CACHE-12 | Redis 等缓存有内存上限和合适 eviction policy | **修改后采用** | 若自管 Redis 必须明确容量和淘汰策略；托管缓存按平台能力配置，不重复造一层资源管理。 |
| CACHE-13 | 持久数据和纯缓存数据必要时隔离 | **按需采用** | 当生命周期、淘汰策略、可用性要求冲突时才分开部署；不因为职责不同就机械多建一个实例。 |
| CACHE-14 | 重要缓存监控命中、淘汰、内存和延迟 | **修改后采用** | 缓存成为关键性能路径时需要这些指标；小型、非关键缓存不必铺设昂贵的完整 dashboard。 |
| CACHE-15 | 缓存失效应尽可能局部化 | **采用** | 全局 flush 会制造缓存冷启动和瞬时负载峰值。优先按对象、租户或版本失效。 |
| CACHE-16 | 高一致性且收益低的数据可以不缓存 | **采用** | 缓存不是目标本身。正确性和可理解性优先于微小延迟收益。 |
| CACHE-17 | 缓存故障时明确降级策略 | **修改后采用** | 若主存储能承受回退，可绕过缓存；若缓存承担保护主存储的关键作用，则可能需要限流或失败关闭。不能默认所有缓存故障都 fail-open。 |
| CACHE-18 | 性能验收视风险测 warm 与 cold cache | **修改后采用** | 对声称依赖缓存的关键路径应检查冷启动或失效后的负载；不是每次小改动都需要完整冷缓存压测。 |

## 第一版结论

当前不建议为 Golf/一般项目默认增加缓存层。先解决 A-03～A-05 的请求拓扑、汇总读模型和无界查询。只有实测证明重复读取仍是主要瓶颈，再按数据陈旧容忍度设计缓存。
