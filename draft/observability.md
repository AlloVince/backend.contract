# 可观测性：逐条评估

> 对应来源：../references/observability.md。主要案例：B-01～B-03、C-03～C-06、D-04～D-07、E-11～E-13。

| ID | 候选原则 | 第一版结论 | 评估理由与边界 |
| --- | --- | --- | --- |
| OBS-01 | 关注延迟、流量、错误、饱和度 | **采用** | 这四类信号能覆盖大部分服务级故障；具体指标按平台可用能力选择，不要求每个小工具都搭建独立监控平台。 |
| OBS-02 | 评估延迟时区分成功与失败请求 | **修改后采用** | 对关键线上服务应看分位数和失败延迟，避免快速失败美化平均值；不必为每个临时脚本建立复杂分析仪表盘。 |
| OBS-03 | 黑盒用户症状和白盒内部指标并用 | **采用** | C-03 证明健康端点不能代表业务可用；只看 CPU 也无法知道用户任务是否成功。两类信号互补。 |
| OBS-04 | 告警优先围绕用户症状 | **采用** | 内部异常未必影响用户；优先告警真实失败、延迟、容量风险，减少无行动价值的噪声。 |
| OBS-05 | 会叫醒人的告警必须可行动 | **采用** | 每个高优先级告警应有明确调查/恢复动作。长期没人处理的告警要调整或删除。 |
| OBS-06 | health 只证明对应检查项 | **采用** | C-03 是直接反例。进程存活、数据库连通和真实训练页可用是不同结论，不能混为一个绿色状态。 |
| OBS-07 | 关键请求有稳定 request/trace ID | **修改后采用** | 对生产 API 与跨组件请求应贯穿关联 ID；不要求所有本地小脚本都接入分布式 tracing。 |
| OBS-08 | 结构化日志而非靠自然语言正则猜字段 | **采用** | 结构化字段更便于查询和关联；但字段要稳定且精简，不应为日志规范堆一套自定义框架。 |
| OBS-09 | 适用时采用 OpenTelemetry 等语义约定 | **采用** | OTel 为日志、指标、trace 提供通用语义，能减少多运行时的字段差异。使用成熟 SDK/平台，不自建同义标准。 |
| OBS-10 | 日志、指标、trace 可通过共同标识关联 | **修改后采用** | 对关键服务应具备合理关联路径；具体系统未必支持每种信号完全互跳，先确保 request/trace ID 和关键错误能定位。 |
| OBS-11 | 区分平台终止、应用异常、客户端错误和日志中断 | **采用** | C-04/C-05 是直接反例。应用日志未完成不能证明没有失败，必须查平台 invocation status、日志和 trace。 |
| OBS-12 | 记录关键资源成本，不只看 HTTP 总时长 | **采用** | B-03 的内部 N+1 无法从请求数看出。关键路径要能观察 SQL 次数/耗时、子请求、CPU、对象存储等。日志不应逐请求记录所有细节而造成成本爆炸。 |
| OBS-13 | 对批量/集合操作记录输入规模 | **采用** | 输入 N 与成本关系是识别 O(N)/N+1 的基础。记录计数和耗时即可，不必泄漏实际业务数据。 |
| OBS-14 | 日志不记录密码、token 或不必要个人数据 | **采用** | 这是安全底线。调试方便不能成为复制秘密和个人数据的理由。 |
| OBS-15 | metrics 避免高基数 ID | **采用** | 将 user/session ID 当标签会导致指标存储和查询成本失控。需要逐对象定位时使用日志/trace，而不是无限基数指标。 |
| OBS-16 | 采样策略尽量保留错误与慢请求 | **修改后采用** | 高流量系统可用 tail sampling 或错误优先策略；小流量项目可更简单。采样不能让关键故障完全不可见，也不能无预算地保留全部 payload。 |
| OBS-17 | 观测数据缺失不能自动解释成正常 | **采用** | D-04、D-06 说明“没有日志/新鲜快照”可能是观测失效。状态要区分正常、异常和未知。 |
| OBS-18 | 排障先查现有平台日志、应用日志、trace 和指标 | **采用** | C-04 直接对应。先使用已有证据，确认缺口后再增加观测，避免先造系统或错误宣称没有数据。 |
| OBS-19 | Dashboard 服务于具体问题，定期清理无用视图 | **修改后采用** | 可以清理重复且无用户的 dashboard；但某些低频事故指标即使平时少看，也可能有重要取证价值，不按浏览次数机械删除。 |
| OBS-20 | 线上验收包含真实用户路径和资源指标 | **采用** | B-02/C-03/C-06 说明启动成功或局部测试通过不够。关键路径需要真实端到端结果与资源成本证据。 |

## 第一版结论

当前最有价值的不是先上大型 APM，而是让每次关键请求能回答：**发生了什么、走过哪些依赖、花了多少资源、失败在哪一层、证据是否完整。** 优先复用 Cloudflare 平台日志与现有工具，再按缺口补 OTel。
