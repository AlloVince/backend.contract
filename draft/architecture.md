# 后端架构与边界：逐条评估

> 对应来源：../references/architecture.md。主要案例：A-01～A-10、B-01～B-03、C-01～C-03、G-01～G-03。

| ID | 候选原则 | 第一版结论 | 评估理由与边界 |
| --- | --- | --- | --- |
| ARCH-01 | 默认先用边界清楚的模块化单体；有真实需要再拆服务 | **采用** | 我们是独立开发者主导，额外服务会增加部署、观测、版本兼容和故障恢复成本。先把模块与数据边界做好，比先拆微服务更符合实际；只有独立扩缩容、部署、故障隔离或团队所有权成为硬需求时再拆。 |
| ARCH-02 | 模块按业务职责和数据责任划分 | **采用** | A-07、A-08、A-09 说明技术目录和数据责任不一致会制造耦合。分层应服务真实职责，不按每种文件或每张表一个服务机械拆分。 |
| ARCH-03 | 同一业务事务尽量留在一个明确一致性边界内 | **采用** | 分布式拆分会把原子事务变成部分成功和补偿问题。先减少跨边界写入；确实跨系统时才设计可恢复流程。 |
| ARCH-04 | 独立服务有 Owner、独立部署理由、契约和故障边界 | **修改后采用** | 对真正独立部署的服务是必要条件；不要求每个代码模块都成为独立服务或拥有完整微服务治理。Owner 文档也不能代替实现质量证据。 |
| ARCH-05 | 不为纯转发增加 BFF / Gateway | **采用** | A-01 已直接证明：前端再经 JS 转发后端 API 并不等于前后端分离。只有认证、聚合、限流、协议适配等具体职责才足以支持中间层。 |
| ARCH-06 | 浏览器直接访问面向浏览器的 API；代理必须有明确理由 | **采用** | 与 Golf 已明确的部署结构一致。不能因为代理常见就默认引入；如有安全或网络限制，应具体说明。 |
| ARCH-07 | 按运行时和数据路径放置计算；静态文件、大对象和重计算不无理由共用请求处理器 | **采用** | A-02、A-09 与 B-01～B-03 表明错误路由会把静态/大对象成本带入 Worker。直出静态资源、对象存储直传直下、重任务拆批，优先于把所有工作塞进 API。 |
| ARCH-08 | Serverless / Edge 不是无限资源，必须核对真实平台限制 | **采用** | Golf 已发生 1102 和请求额度风险。Cloudflare 官方文档在 2026-10 仍明确列出 CPU、内存、子请求、连接数和每日请求限制；精确数值应按实际套餐与配置读取，不能硬编码成跨平台统一阈值。来源：https://developers.cloudflare.com/workers/platform/limits/ |
| ARCH-09 | 优先使用托管平台原生能力，除非自建有明确收益 | **修改后采用** | 对当前团队，D1/R2/托管部署等可减少运维面；但托管不自动更便宜或没有限制。比较配额、计费、可观测性、恢复和迁移成本后再选。 |
| ARCH-10 | 多种存储由访问模式、事务、成本或数据类型驱动 | **采用** | 数据库、对象存储、缓存各自适合不同职责；A-09 显示把备份和产品对象混在一起会造成生命周期问题。反过来，也不应为现代化而堆叠数据库。 |
| ARCH-11 | 同步调用满足即时需求；队列只在削峰、重试、独立执行等有价值时引入 | **采用** | MSG-20 与 E-02/G-03 的反例共同说明，异步基础设施会引入状态、重放、观测和恢复成本。简单且有界的工作保持同步更好。 |
| ARCH-12 | API-first 使用机器可读契约，并验证真实实现 | **采用** | REST-18/19 和 D-05 表明契约文件与真实工具/入口可能漂移。OpenAPI 3.2.1 于 2026-09 发布；重点是从契约生成/验证并核对真实生产行为，而不是追逐版本号。来源：https://spec.openapis.org/oas/v3.2.1 |
| ARCH-13 | 使用标准协议和通用可观测语义，降低迁移成本 | **采用** | OpenTelemetry Semantic Conventions 覆盖 traces、metrics、logs 等通用概念，有利于跨语言和平台统一；采用标准语义不等于必须一次引入完整观测平台。来源：https://opentelemetry.io/docs/specs/semconv/ |
| ARCH-14 | 避免聊天式细粒度服务调用，让一个请求完成一个明确用户任务所需的数据读取 | **采用** | A-03、A-05、B-03 是直接反例。API 不应让前端为了一个页面串起几十个请求，也不能只看 HTTP 数量而忽略 endpoint 内部 N+1。 |
| ARCH-15 | 多模块共享数据库时明确表/字段所有权和写入边界 | **采用** | A-08 是直接治理目标。Golf 已明确设备导出数据与用户/教练数据分开；外键按用户提出的同一数据颜色边界治理，跨颜色外键禁止。颜色规则是该项目约束，不直接强加给所有项目。 |
| ARCH-16 | 先保证内聚、依赖方向、测试和发布可靠，再引入复杂基础设施 | **采用** | G-01～G-03 表明治理机制本身会成为故障源。微服务、Service Mesh、复杂编排不应作为默认现代化步骤。 |
| ARCH-17 | 技术选型比较全生命周期成本 | **采用** | 当前约束不只是 CPU，还包括 Agent 上下文、部署额度、人工授权、观测和恢复成本。不能只比较 benchmark 或单次开发速度。 |
| ARCH-18 | 架构图和目录不是最终证据，需核实真实请求路径、部署入口和数据流 | **采用** | A-01、C-01、C-03、D-05 已反复证明源码结构与真实运行入口可能不一致。必须从浏览器、生产端点、平台日志和实际数据行为验收。 |

## 技术趋势结论

- **模块化单体优先，不等于反对微服务。** 微服务有独立部署和扩缩容收益，但也引入网络、版本、事务和观测成本；成熟指南同样要求先评估组织与运维准备度。https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/microservices-assessment
- **Serverless / Edge 要以平台约束为设计输入。** 不能只因为托管平台会自动扩缩，就假定单次请求可以做任意计算或任意多次子请求。https://developers.cloudflare.com/workers/platform/limits/
- **契约与可观测性正在标准化。** OpenAPI 与 OpenTelemetry 能降低手工同步成本，但必须验证实际部署与消费端，不能只维护一份看起来正确的文档。
