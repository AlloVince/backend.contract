# 架构与设计 Review：领域模型、命名、API、数据约束与操作面

> **状态：历史草案。** 用户已确认正式采用，现行权威规则见 [contract/DESIGN-REVIEW.md](../contract/DESIGN-REVIEW.md)。本文保留原始评估过程；如有差异，以正式规范为准。
>
> 本文是**设计阶段的 Review 标准**：在实现前检查概念、边界和操作方式是否清晰。它补充 `contract/REVIEW.md` 的实现后证据审查，不替代现有架构、API、数据规范。

## 目标

设计 Review 的核心不是检查是否用了某种架构模式，而是确认：

- 系统要表达的事物是否被准确提炼，概念是否有稳定、唯一的名字；
- 单体、集合、关系和跨实体读模型是否清晰区分；
- API、数据库和代码中的命名是否表达同一套领域语义；
- 数据约束是否帮助系统，而不是无意间绑定独立演进的生命周期；
- 页面、CLI、配置是否让人和 Agent 都能直接、低成本地使用系统。

设计 Review 应优先在写代码前完成。它是 Agent 的持续判断责任，不应默认变成审批、冻结或自锁流程。

## 候选原则与初步评估

### DESIGN-01｜实体的提炼（Entity Refinement）

**初步结论：采用。主要由 Agent Review。**

领域模型首先要回答：系统里究竟存在什么事物？每个重要概念都应有一个经过斟酌、能够长期复用的名称。

一个被提炼出来的领域概念，应当能够用一个词稳定表达，而不是每次都要附带一段解释才能知道它指什么。名称背后至少要明确：

- 它是什么，以及明确不是什么；
- 它的身份如何确定，生命周期是什么；
- 谁拥有它，谁可以创建、修改和删除；
- 它与其他实体、值对象和关系的边界；
- 它的权威事实来源是什么。

需要区分：

- **Entity**：有独立身份和生命周期的领域对象；
- **Value Object**：由值定义、通常没有独立身份的对象；
- **Relationship**：实体之间具有独立业务含义的关系；
- **Collection**：同类实体的集合；
- **Read Model / Projection**：为了查询或展示组合出来的只读结果；
- **DTO / Persistence Model**：传输或持久化结构，不自动等于领域实体。

不要把每个名词都提升为 Entity，也不要为了看起来符合 DDD 而制造 Aggregate、Repository 或 Service。提炼的目标是减少概念歧义和重复解释，不是增加模型层级。

**参考：** yinxing.js 中的 `WorkElection`、`PersonCatalog`、`WorkPersistence` 等命名分别表达了明确的业务职责。它们可作为命名与职责提炼的参考，不意味着照搬其所有实现。

### DESIGN-02｜英文命名与单复数语义

**初步结论：采用。主要由 Agent Review；局部命名约定可由工具辅助。**

默认约定：

- 单数表达一个实体或单个实例；
- 复数表达同类实体的集合；
- 变量、类型、模型、表名和 API 路径应保持一致且可预测的映射；
- 选择区分度高、指向明确的词，避免用 `Message`、`Data`、`Info` 等过宽的词承载多个不同概念；除非它确实就是一个定义清楚的领域概念；
- 如果某个英语名词单复数同形，容易导致单体和集合无法区分，优先改用含义准确、单复数清晰的近义词；
- 不规则但能够清晰区分的复数形式可以使用；若标准术语、外部协议或既有兼容性使替换不合理，应明确记录例外，而不是机械改名。

命名不能只看词典释义，还要看它在当前领域中的边界。一个名称应尽可能只承载一个稳定含义；同一个词不应在不同模块里悄悄指向不同范围。

**参考：** yinxing.js 的领域代码使用 `WorkElection`、`PersonCatalog` 等单数领域词描述职责，实体集合使用 `Works`、`Sources`、`Persons`。评审时应关注概念和集合是否能被清晰区分，而不是只检查字符串是否以 s 结尾。

### DESIGN-03｜REST 资源与实体边界

**初步结论：采用。与现有 API Contract 及 Golf Owner 保持一致。**

标准资源接口应清晰表达一个领域实体或一个有独立业务含义的关系实体：

- 集合接口表达一个实体集合，通常使用复数资源名；
- 单体接口表达一个实体，通常使用集合资源路径加稳定 ID（例如 /users/{id}）；
- 嵌套路径可以表达查询范围，例如 `/users/{userId}/sessions` 返回 Session 集合，而不是把 Sessions 塞进 User 的标准表示；
- 允许返回必要的关联 ID、关系状态或有明确边界的轻量字段；
- 慎重把其他实体的完整对象、集合或统计值嵌入当前实体响应，避免一个实体的 API 逐渐变成不受控的跨实体聚合；
- 稳定且确有业务价值的跨实体查询，应设计成独立命名的只读 Read Model / Query Resource，明确组合范围、消费者、分页和响应上限；
- 确实需要跨实体写入时，应明确设计为业务 Action / Command，说明涉及的实体、副作用、授权、原子性、幂等与失败恢复，不隐藏在普通 CRUD 中。

这不等于禁止 SQL JOIN、视图或内部组合查询。约束的是对外 API 的资源语义，而不是内部如何读取数据。

也不应为了追求“纯 REST”而把所有业务动作硬塞进 CRUD。搜索、报告、分析和命令式操作可以使用明确的查询资源或 Action。

**已有依据：** `contract/API.md` 已要求从消费者任务和领域概念设计 API；Golf Owner §3.4 已明确标准资源接口的实体边界。本条主要补充命名、集合/单体和跨实体响应的设计评审。

### DESIGN-04｜用户数据的外键、触发器、存储过程与视图

**初步结论：修改后采用。需要由项目 Owner 声明适用边界。**

记录的设计偏好：

- 面向用户、需要独立演进的业务数据表，默认不使用数据库外键；实体之间保存稳定 ID，由应用程序负责关联解析和完整性维护；
- 默认不使用数据库 Trigger 和 Stored Procedure；业务行为、审计和关联更新由应用代码显式完成；
- View 可以有限使用，主要用于稳定、只读的查询投影；不应成为隐藏业务规则或新的写入入口；
- 不因为拒绝外键而删除主键、唯一约束、NOT NULL、CHECK、必要索引或事务。它们解决的问题不同，仍应按真实不变量使用。

这样做主要是为了减少数据生命周期和发布演进之间的隐式耦合，降低跨模块、跨服务、批量导入、独立重建和在线升级时的协调成本。

**需要避免的误解：**

1. 不能笼统声称外键必然造成严重性能问题。它的实际成本取决于数据库引擎、索引、写入路径和数据规模；更值得关注的是引用两端的生命周期、迁移顺序、删除语义和部署耦合。
2. 不使用外键后，完整性责任不会消失。应用必须明确检查引用是否存在、如何处理并发写入、删除或重建后的孤儿引用，以及如何定期发现不一致。单纯的“先查再写”不能独自解决并发竞态。
3. Trigger / Procedure 隐藏了额外写入路径，容易让代码、迁移、测试、审计和运行行为分散在不同地方。默认由应用显式执行更容易追踪和跨语言维护。
4. View 应保持用途有限、语义稳定、可追踪；不能通过 View 把多个实体拼成一个含义不清的标准实体响应。

**建议的默认适用范围：**

- 用户/业务数据、跨 Owner 的引用、需要独立部署或重建的模块：默认不用外键，跨边界只保存稳定 ID；
- 同一数据库、同一 Owner、同一发布与重建生命周期内的封闭内部数据：只有在外键带来明确完整性收益、且不会妨碍演进时才考虑例外；
- Trigger / Stored Procedure：默认禁止，只有平台能力或经过验证的性能/一致性需求足以证明必要性时才考虑例外。

**真实项目对照：** 当前 Golf 并非完全无外键。其架构允许同一数据颜色内的外键，禁止跨颜色外键；Trigger / Stored Procedure 则由架构测试明确禁止。若未来采用更严格的“用户数据表默认无外键”，这属于对现有 Golf 规则的进一步收紧，需要单独确认，不能误称为当前实现。

### DESIGN-05｜页面初始加载的业务 API 数量

**初步结论：采用为 Review 触发条件，不作为跨项目性能 Gate。**

用户提出的默认判断标准：

> 一个页面从打开到主要功能加载完成，如果需要超过 3 个业务 API，应检查页面设计或 API 设计是否存在问题。

统计范围：

- 统计当前页面首次进入时，为完成默认主要业务内容而发起的业务 API；
- 不统计静态资源请求；
- 不统计全站共享的用户状态、顶部用户信息等全局加载；
- 不统计用户主动操作后才触发的请求；
- 延迟加载的非首屏、非默认功能应单独说明，不应混入初始关键路径。

超过 3 个业务 API 时，至少检查：

- 是否存在请求瀑布、重复读取或多个接口返回重叠数据；
- 是否把一个完整业务概念拆成多个过细的接口；
- 是否缺少合适的服务端读模型；
- 是否有页面专属聚合接口，或相反，一个接口承载了过多无关数据；
- 是否有 N+1、重复数据库查询或大对象被无意义加载。

**边界：** 3 是设计 Review 的触发阈值，不是所有平台、所有页面的性能定律。并行的 4 个轻量请求可能优于一个慢而臃肿的聚合接口；真正要判断的是关键路径、请求依赖、数据重复和整体资源成本。不能为了满足数字而制造一个返回所有东西的万能 API。

### DESIGN-06｜CLI 是人和 Agent 共享的正式操作面

**初步结论：采用。Agent 持续遵循，重复操作可做项目级 Gate。**

CLI 不只是开发者的辅助脚本，而是人和 Agent 共用的正式操作入口。

日常重复工作原则上应通过同一套 CLI 完成，包括：

- 开发、启动、停止、状态查询和诊断；
- 数据导入、导出、重建、迁移和校验；
- 批处理、维护、审计和恢复；
- 项目日常运维中需要重复执行的其他操作。

不应让 Agent 依赖一套人类不知道、无法复用的私有脚本，也不应让人每次为了完成常规操作临时编写代码。

一次性调查或临时实验可以使用临时脚本；一旦操作重复出现或成为正式工作流，就应评估是否纳入正式 CLI。

CLI 应提供人类可读的帮助、明确的退出状态和错误信息；需要自动消费时，提供稳定的机器可读输出。长任务应报告进度、阶段和最终结果，不能长时间静默。

### DESIGN-07｜CLI 参数与默认值

**初步结论：采用。主要由 Agent Review，参数行为可由测试验证。**

- 必需参数才要求用户显式提供；
- 可推导或有合理默认值的参数应使用默认值；
- 不要求每次调用都重复输入所有默认配置；
- 默认值应在 `--help` 等帮助信息中可见；
- 通过少量明确参数覆盖默认行为，而不是设计大量重复、互相覆盖的选项；
- 参数名称应表达业务含义，不暴露内部实现细节；
- 破坏性操作不能仅因为“参数简化”就使用危险的隐式默认范围；应让影响范围和执行结果可预期。

CLI 的目标是让常见路径足够简单，同时保留必要的精确控制。

### DESIGN-08｜分层配置与接近自启动的项目默认状态

**初步结论：采用。配置合并和必需项可 Gate，配置结构由 Agent Review。**

配置文件负责表达项目默认行为和环境差异，环境变量不应成为所有普通配置的搬运容器。

建议的配置结构：

1. `config.default.*`：所有环境通用的安全默认值；
2. `config.{environment}.*`：开发、测试、生产等环境的差异；
3. `config.local.{environment}.*`：本机或部署实例的私有覆盖，纳入 Git 忽略；
4. `.env` / 环境变量：密钥、凭据，以及确实需要由部署环境注入的动态值。

合并顺序和覆盖规则必须明确、可预测，并经过测试。尤其要明确嵌套对象、数组和显式 `null` 的合并行为，不能只写“deep merge”而没有定义语义。

目标状态：

- 新项目初始配置已经包含各环境合理的默认行为；
- 开发环境尽可能开箱可运行；
- 生产环境只需提供真实部署目标和必要秘密，不需要把所有普通配置重新抄一遍；
- 环境变量只覆盖真正需要变化的值，不重复声明已有默认值；
- 启动时校验必需配置，缺少凭据时给出明确、可操作的错误；
- 提供不含秘密的配置示例，让使用者能看懂项目需要哪些配置。

**参考：** yinxing.js 文档记录了 `config.default` → `config.{NODE_ENV}` → `config.local.{NODE_ENV}` 的覆盖层次，体现了按环境组织配置的方向。

**边界：** yinxing.js 当前默认配置中仍有不少 `process.env` 读取，环境文件也存在数据库占位值。因此应借鉴它的分层方式，而不是把当前所有配置项和环境变量用法原样复制。Backend Contract 的目标是进一步做到默认配置完整、秘密配置最少、环境差异清晰。

## 初步保障方式

| 原则 | Gate 候选 | Agent 责任 | Review 责任 |
|---|---|---|---|
| 实体提炼 | 不做通用语义 Gate；稳定词汇表可做结构校验 | 定义概念、身份、边界和 Owner | 检查概念是否重叠、遗漏或被错误合并 |
| 单复数与命名 | 局部 lint / schema 命名测试 | 选择准确词汇并保持跨层一致 | 检查歧义、错误抽象和领域语义 |
| REST 资源边界 | OpenAPI / 响应结构 / 行为测试 | 设计集合、单体、关系和读模型 | 检查真实消费者与跨实体边界 |
| 数据库约束 | 项目明确选择后，检查 schema 和 migration | 说明是否采用 FK、Trigger、Procedure 及原因 | 检查升级、重建、并发和引用完整性 |
| 页面 API 数量 | 真实页面网络测试可采集，不默认做通用硬门禁 | 超过 3 个时主动触发设计检查 | 检查关键路径、请求拓扑、N+1 和响应成本 |
| CLI 共享操作面 | 重复操作入口和行为测试 | 常规操作优先走正式 CLI | 检查人和 Agent 是否真的能用同一入口完成工作 |
| CLI 默认参数 | help / 参数解析 / 默认行为测试 | 简化常见调用路径 | 检查默认值是否安全、清晰、可预测 |
| 分层配置 | 合并顺序、配置 Schema、启动校验测试 | 保持配置分层和默认值完整 | 检查环境迁移、秘密管理和真实部署可用性 |

同一原则可以同时由 Gate、Agent 和 Review 保障。不要为了覆盖率给领域语义、架构取舍或性能判断制造不可靠的自动门禁。

## 与现有 Contract 的关系

本草案不重复定义已经存在的规范：

- `contract/ARCHITECTURE.md`：模块边界、运行路径和复杂度控制；
- `contract/API.md`：领域 API、HTTP 语义、分页、请求扇出；
- `contract/DATA.md`：数据 Owner、身份、事务和 Schema；
- `contract/AGENT.md`：Agent 的设计与开发行为；
- `contract/REVIEW.md`：实现后的证据采集与结果判断；
- `contract/GATES.md`：Gate / Agent / Review 的保障映射。

本草案新增的重点是：**实体的提炼、命名的单复数纪律、用户数据的外键默认偏好、页面 API 数量触发 Review、CLI 人机共享操作面、CLI 默认参数，以及分层配置的设计目标。**

其中，外键偏好与当前 `draft/mysql.md` 的“按项目边界决定”存在更严格程度上的差异；正式采用前应先确定适用范围，不直接改写现有正式规范。

## 后续评审顺序

1. 先确认每条原则的适用边界和例外，不直接把草案转成 Gate。
2. 对照更多实际消费者，检查是否有反例或过度约束。
3. 明确哪些内容进入 Agent 设计 Review，哪些可以复用现有工具测试。
4. 只有经过确认的跨项目通用原则，才从 Draft 提炼进入 `contract/`。
