# REST API：逐条评估

> 对应来源：../references/rest-api.md。主要案例：A-01、A-03～A-07、B-02～B-03、C-03、D-05、E-11～E-13。

| ID | 候选原则 | 第一版结论 | 评估理由与边界 |
| --- | --- | --- | --- |
| REST-01 | API 从消费者任务和读模型设计，而不是逐表暴露 | **采用** | A-05 说明按表拆资源会把汇总工作推给前端。先从页面/业务任务出发，再选择资源 API 与读模型。 |
| REST-02 | URL 表达资源，标准 HTTP 方法表达常规 CRUD | **修改后采用** | 对资源型接口有利于一致性；但命令式任务、复杂分析并不总能优雅映射成 CRUD，不为追求“纯 REST”牺牲清晰语义。 |
| REST-03 | 同类资源命名、复数、层级和 ID 保持一致 | **采用** | 低成本、高复用性，能降低 Agent 与消费者猜测。规范应简洁，不必为词形差异增加复杂检查。 |
| REST-04 | 不泄漏内部类名、表名和存储路径 | **采用** | 内部实现经常变化，公共 API 应表达稳定业务语义。A-08/A-09 也说明数据库和存储结构不能直接当业务模型。 |
| REST-05 | GET 只读，不隐藏业务副作用 | **采用** | 浏览器预取、代理重试、缓存和爬虫都可能触发 GET。把写操作藏在 GET 会导致不可预测副作用。 |
| REST-06 | 正确使用 HTTP 方法和状态码，不统一返回 200 | **采用** | 真实错误状态对客户端重试、监控、缓存和定位都有影响；C-03 也表明状态码不能代替业务验收，但仍需准确表达请求结果。 |
| REST-07 | 增长型集合有分页或硬上限 | **采用** | A-04、B-02 直接对应。不能把全量读取再由前端切片视为分页。 |
| REST-08 | 分页具有稳定排序 | **采用** | 无稳定排序时翻页可能重复或漏项。若数据持续变化，还需明确游标语义；不要承诺分页快照一致性而没有实现。 |
| REST-09 | 列表只返回当前用途需要的字段 | **修改后采用** | 大型序列、文件和重对象不应默认随列表返回；但不要把 API 切成无数个微型接口，需结合真实页面读模型。 |
| REST-10 | 提供真实需要的过滤、排序、字段选择 | **按需采用** | 列表常有价值，但不要求每个 endpoint 都实现任意查询 DSL。只支持明确消费者需要且能安全执行的查询条件。 |
| REST-11 | 高频稳定汇总可由服务端提供 read model / summary | **采用** | A-05 是直接反例。汇总可即时 SQL 计算，也可物化；选择由数据规模、更新频率和一致性要求决定，不机械建汇总表。 |
| REST-12 | 同页大量请求时检查 API 粒度和读模型 | **采用** | A-03、B-03 表明请求扇出会把一次页面访问放大。不要简单要求“减少请求数”，要一起检查请求是否必要及内部查询复杂度。 |
| REST-13 | 纯转发 BFF / proxy 必须有具体职责 | **采用** | A-01 直接对应。中间层只有提供认证、聚合、协议适配、限流或其他真实价值时才保留。 |
| REST-14 | 错误响应结构统一且机器可处理 | **修改后采用** | 至少统一错误类型、可读说明和关联 ID；是否完整采用 RFC 9457 Problem Details 取决于客户端生态，避免为了标准增加重复封装。 |
| REST-15 | 可修复的客户端输入错误返回明确 4xx | **采用** | 400/404/409/422 等应按语义使用；不要把无效参数当 500，也不要让客户端只能解析错误文案猜类型。 |
| REST-16 | 公共错误不泄漏堆栈、SQL、密钥和内部路径 | **采用** | 这是安全基线，SEC-13 同样覆盖。内部诊断留在受控日志，响应只返回安全的错误信息和关联标识。 |
| REST-17 | 优先向后兼容；破坏性变更才做明确版本策略 | **修改后采用** | 新增可选字段等兼容变化不应机械升主版本；确有破坏性变化时要有迁移/弃用期。不要为了“版本管理”给每个 API 提前加版本层。 |
| REST-18 | API 契约机器可读，优先使用 OpenAPI | **采用** | OpenAPI 3.2.1 是当前正式规范之一，可供文档、客户端生成和契约测试使用。要选工具实际支持的版本，不必盲目追最新小版本。来源：https://spec.openapis.org/oas/v3.2.1 |
| REST-19 | OpenAPI / Schema 与真实生产行为一致 | **采用** | D-05 是直接反例：源码有工具不代表真实连接已暴露。检查必须覆盖实际部署入口和消费者，不只校验 YAML 语法。 |
| REST-20 | 可能重复执行的写操作设计幂等语义 | **修改后采用** | 创建订单、提交长任务等确有需要；普通确定性更新可能用唯一约束或 PUT 语义即可。不要为每个写接口都造幂等存储表。 |
| REST-21 | API 的资源成本有边界 | **采用** | 请求大小、记录数、批量规模和执行成本都应可控。边界依据平台配额和业务需要制定，不设无来源的统一数字。 |
| REST-22 | 评审真实 SQL / 存储调用，避免 endpoint 内部 N+1 | **采用** | B-03 是直接反例。HTTP 请求少不等于后端工作少；热点路径要检查查询次数、对象存储请求和随 N 增长的成本。 |
| REST-23 | 慢任务提供可查询状态和最终失败 | **修改后采用** | 对长时间、可恢复、用户需要追踪的任务应提供状态资源；短小且快速完成的工作不必被改造成异步任务系统。 |
| REST-24 | 用真实消费者路径验收 API | **采用** | 单元测试不证明部署、认证、CORS、路由、数据和资源成本都正确。关键路径至少做真实请求或浏览器端到端验收。 |
| REST-25 | 同一业务概念保持权威语义一致 | **修改后采用** | 避免相同概念在多个接口计算出互相矛盾的定义；但列表、详情、图表可以有不同读模型，只要口径和来源明确。 |

## 第一版结论

优先进入正式 Contract 的是：**消费者优先、列表有界、读模型匹配页面、真实调用拓扑可核实、契约与生产一致、错误语义明确**。不要把“REST”理解成每张表都要有 CRUD endpoint。
