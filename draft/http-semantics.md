# HTTP 语义：逐条评估

> 对应来源：../references/http-semantics.md。主要案例：A-01～A-03、C-03、C-06、D-05。

| ID | 候选原则 | 第一版结论 | 评估理由与边界 |
| --- | --- | --- | --- |
| HTTP-01 | GET、HEAD、OPTIONS 等安全方法不承载业务写入 | **采用** | 代理、预取、爬虫和缓存可能自动调用安全方法。读请求不能隐式修改业务状态。 |
| HTTP-02 | PUT、DELETE 等幂等方法保持重复调用不重复产生业务效果 | **采用** | 重试是正常网络现实。响应状态可以因资源是否存在而不同，但重复请求不应重复执行业务副作用。 |
| HTTP-03 | POST 不默认安全重试；必要时设计幂等键 | **采用** | 响应丢失时客户端不知道操作是否已成功。只有操作语义或幂等机制明确时才能自动重试。 |
| HTTP-04 | 2xx、4xx、5xx 准确表达请求结果 | **采用** | 状态码帮助客户端、代理和监控区分输入错误与服务故障。不要一律 200 再解析 body。 |
| HTTP-05 | 资源不存在使用 404，不用 200 + null 掩盖 | **修改后采用** | 目标资源不存在通常应 404；但某个合法资源内的可选字段为 null，或查询本身返回空集合时，200 是合理的。需区分资源不存在与字段缺值。 |
| HTTP-06 | 方法不允许时使用 405，并准确表达 Allow | **采用** | 标准语义能让客户端识别错误；仅在确实是“资源存在但方法不支持”时使用，不能替代所有权限错误。 |
| HTTP-07 | 创建资源适用时返回 201 和新资源位置 | **采用** | 有助于客户端继续读取刚创建的资源；对于不创建新资源的命令不强制使用 201。 |
| HTTP-08 | 无响应体的成功操作可返回 204 | **按需采用** | 是标准选项，不需要为了统一返回无意义 JSON；是否采用应与客户端约定保持一致。 |
| HTTP-09 | 用 Cache-Control、ETag、Last-Modified 等标准缓存机制 | **采用** | 标准机制能被浏览器、CDN 和代理理解；不要另造私有缓存协议。缓存敏感数据时必须同时考虑权限和共享缓存风险。 |
| HTTP-10 | 合适的 GET 使用条件请求减少重复传输 | **按需采用** | 对大响应、静态资源和稳定读模型有价值；对很小或高度动态的响应，收益可能低于实现成本。 |
| HTTP-11 | Range / 大文件下载遵循标准语义 | **采用** | 大文件不应通过应用层整文件缓冲伪装 Range。需确认对象存储、CDN 和 API 各层的实际支持。 |
| HTTP-12 | Content-Type 描述真实响应体 | **采用** | 避免客户端猜格式，也减少内容嗅探风险。上传类型不能仅相信客户端声明。 |
| HTTP-13 | 不把内部异常文本放进公共响应 | **采用** | 内部堆栈、SQL 和路径只进受控日志；对外给稳定错误类型与关联 ID。 |
| HTTP-14 | 按临时/永久及方法保留语义选择重定向状态码 | **采用** | 301/302/303/307/308 行为不同，错误使用可能改变请求方法或影响缓存。按实际重定向意图选择。 |
| HTTP-15 | CDN、Worker、代理不能悄悄改变业务语义 | **采用** | A-01、A-02 说明中间层不只是部署细节；它会改变调用拓扑、缓存、资源成本和错误表现，必须纳入端到端验收。 |
| HTTP-16 | CORS 策略明确，不把全开放作为默认修复 | **修改后采用** | 需要凭据的浏览器请求不能随意使用通配来源；公开无凭据 API 可以允许宽松来源。CORS 不是身份认证或授权。 |
| HTTP-17 | 请求体、响应体和头部大小有合理边界 | **采用** | 防止无界资源消耗和平台限制触发。限额按业务与托管平台设定，不编造跨项目统一数字。 |
| HTTP-18 | 压缩、缓存、Range 等优化只在有收益时启用 | **采用** | 不为追求“最佳实践齐全”机械增加层；先看数据大小、访问频率和平台已经提供的能力。 |

## 第一版结论

HTTP 语义本身是低成本、高收益的公共契约，适合较多直接采用。需要保留弹性的主要是缓存策略、404 与可空字段的边界、CORS 范围和优化是否值得。
