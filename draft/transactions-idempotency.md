# 事务、幂等与重试：逐条评估

> 对应来源：../references/transactions-idempotency.md。主要案例：A-03、A-06、B-02～B-03、C-01～C-02、D-02、E-11～E-13、G-01～G-03。

| ID | 候选原则 | 第一版结论 | 评估理由与边界 |
| --- | --- | --- | --- |
| TX-01 | 事务围绕业务不变量，不把整个请求生命周期都包进事务 | **采用** | 事务应保护一致性，而不是用一个大锁把所有操作包起来。 |
| TX-02 | 事务尽量短，不等待网络、文件、队列或人工操作 | **采用** | 外部等待会持有锁、连接和快照，放大拥塞；先在事务外完成可准备工作。 |
| TX-03 | 先明确原子性边界，再选择事务实现 | **采用** | 数据写入边界不清容易造成部分成功。先定义哪些结果必须同时成立，再决定 SQL transaction、状态机或补偿。 |
| TX-04 | 并发写明确采用锁、约束或原子更新策略 | **采用** | “一般不会同时发生”不是并发控制。优先选择最简单可证明正确的方案，例如唯一约束或条件更新，不默认加复杂分布式锁。 |
| TX-05 | 死锁可发生，事务级重试必须安全 | **采用** | 数据库死锁是并发现实。重试应重新执行完整事务，并确保事务外副作用不会重复。 |
| TX-06 | 重复到达的业务命令设计业务级幂等 | **采用** | 网络超时、队列重复投递和用户重复点击都可能重放操作。幂等应围绕业务结果定义，而非仅记录请求是否见过。 |
| TX-07 | 一个幂等键对应一个逻辑操作和确定 payload | **采用** | 同一键带不同 payload 时应明确拒绝或返回原结果，不能静默复用错误结果。 |
| TX-08 | 幂等结果有明确保存期限、作用域和冲突行为 | **修改后采用** | 对确实需要幂等键的操作有必要；保存多久按业务重试窗口决定，不把永久保存当默认。 |
| TX-09 | 客户端重试复用原幂等键 | **采用** | 每次重试重新生成 key 会把同一逻辑操作伪装成多个新操作，失去保护效果。 |
| TX-10 | 非幂等写请求不能被多层无条件重试 | **采用** | SDK、网关、应用和队列若都重试，会放大请求与副作用。重试责任应集中，并依据操作语义。 |
| TX-11 | 所有远程调用有合理超时 | **采用** | 无限等待会占用资源并拖住上游。超时应按调用目的与总预算设定，不要求所有调用用同一个值。 |
| TX-12 | 瞬时失败重试用指数退避与 jitter | **采用** | 同步重试容易形成重试风暴。对限流、不可重试错误和已超出总预算的调用应停止重试。 |
| TX-13 | 重试有次数上限或总时间预算 | **采用** | 失败下游不能被持续重试压垮；失败应最终暴露并可观测。 |
| TX-14 | 只在合适的一层负责重试 | **采用** | 多层重试会乘法放大请求。应明确由 SDK、服务或队列中的哪一层负责，其他层不再重复重试。 |
| TX-15 | 不假设数据库写入和消息发送会自动保持一致 | **采用** | 双写存在部分成功窗口。必须明确丢失/重复事件如何恢复，而不是依赖时序碰巧成功。 |
| TX-16 | 跨系统一致性按需采用 outbox / saga 等模式 | **修改后采用** | 当数据库提交和事件发布必须可靠关联时 outbox 有价值；跨多个业务服务的长流程可能需要 saga。普通单数据库业务不应为了架构先进而引入这些模式。 |
| TX-17 | 外部操作成功但响应丢失时可恢复确定结果 | **采用** | 幂等键、操作状态查询或上游唯一 ID 能避免“猜测是否成功”并导致重复副作用。 |
| TX-18 | 对 exactly-once 声明明确保证范围 | **采用** | 单个 broker 的语义不能自动保证外部数据库、对象存储和第三方 API 的副作用恰好一次。跨系统仍需幂等和恢复。 |
| TX-19 | 失败恢复覆盖部分成功 | **采用** | 真实系统常在多步骤之间失败。只测试全成功/全失败会漏掉最危险的中间状态。 |
| TX-20 | 对重试与补偿执行真实故障测试 | **修改后采用** | 对有重试、外部副作用或部分成功路径的关键操作必须测；不要求每个纯函数都做故障注入。 |

## 第一版结论

正式 Contract 应优先保留：**短事务、幂等写入、单层重试、超时和预算、部分成功可恢复**。分布式事务替代模式按真实跨系统一致性需求启用，不能把 outbox/saga/队列当成所有项目的默认底座。
