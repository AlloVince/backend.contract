# 可靠性与发布：逐条评估

> 对应来源：../references/reliability-deployment.md。主要案例：A-02、B-01～B-05、C-01～C-06、D-02～D-07、E-03、E-08、G-01～G-03。

| ID | 候选原则 | 第一版结论 | 评估理由与边界 |
| --- | --- | --- | --- |
| REL-01 | 构建尽量可重复 | **修改后采用** | 同一 commit 和受控依赖应生成可追溯产物；不要求所有构建字节级完全确定，但必须知道线上实际部署的是哪个版本。 |
| REL-02 | 构建、测试、发布自动化 | **采用** | Golf 已明确要求常规发布语义化自动完成。自动化应复用平台能力，避免每次临时脚本；数据库变更等特殊步骤需显式治理。 |
| REL-03 | 同一生产服务有唯一发布责任 | **采用** | C-01 直接对应。concurrency 只控制并发，不等于消除重复发布触发。应明确哪个 workflow/仓库负责哪个部署目标。 |
| REL-04 | 发布变更小而可解释 | **修改后采用** | 小变更有助定位和回滚，但不应为遵守“小提交”而把一个目标拆成用户需多次启动的碎片。按风险与独立验收边界拆分。 |
| REL-05 | 高风险变更渐进发布 / canary | **按需采用** | 对流量大、影响面大且平台支持的服务有价值；小型项目不必为了形式引入复杂流量分层。最重要的是可恢复和真实观察。 |
| REL-06 | 发布前明确回滚或前滚方案 | **采用** | 数据迁移、不可逆变更尤其需要。对纯静态且可立即回滚的发布，方案可以很简单，不必另建审批系统。 |
| REL-07 | 发布异常先恢复服务，再做深度分析 | **采用** | 生产故障时用户影响优先；保留足够证据后快速回滚/修复，再分析根因。 |
| REL-08 | Schema、配置和代码考虑新旧版本共存 | **采用** | 独立发布和多仓现实意味着它们可能短暂不同步。迁移应兼容窗口中的旧代码与新代码。 |
| REL-09 | 配置变更也要可追踪、可恢复 | **采用** | 配置能改变路由、额度、权限和运行时行为，风险不低于代码。应版本化或以平台审计记录追踪。 |
| REL-10 | 远程调用有超时 | **采用** | 防止资源无限占用。超时按总请求预算和下游行为设置，不使用一个全局硬编码值。 |
| REL-11 | 只对可安全重试的瞬时错误重试 | **采用** | 非幂等操作重复执行会制造副作用。与 TX-10/TX-12 共用一个重试原则，避免每层各自发明实现。 |
| REL-12 | 过载时使用限流、背压或降级 | **采用** | 请求放大时无限并发只会加重故障。先减少不必要工作、设资源边界，再按业务需要降级；不要把所有错误都转成静默成功。 |
| REL-13 | readiness 与 liveness 分开 | **按需采用** | Kubernetes 等编排环境有明确语义；Cloudflare Worker 等托管运行时未必暴露这套探针。保留“是否可接流量”和“是否需要重启”是不同判断的原则，不强制实现两种 endpoint。 |
| REL-14 | 避免错误 liveness 造成级联重启 | **按需采用** | 适用于有探针和自动重启的运行平台。健康判断应验证本地进程是否可恢复，不应把暂时下游故障都当成进程死亡。 |
| REL-15 | 长生命周期服务优雅关闭 | **按需采用** | 对 worker、队列消费者和常驻服务重要；短生命周期请求函数由平台管理生命周期时，应遵循平台机制，不自造 shutdown 框架。 |
| REL-16 | 健康验收包含真实关键用户路径 | **采用** | C-03/C-06 直接对应。health 只能证明检查项；关键页面、认证和数据路径需实际请求或浏览器验证。 |
| REL-17 | 发布后观察错误、延迟、流量、饱和度和业务指标 | **采用** | deploy 成功不等于业务成功。先利用平台现有指标/日志；监控深度按系统风险决定。 |
| REL-18 | 性能门槛来自平台、SLO 或实测基线 | **采用** | B-05 直接对应。没有来源的毫秒/并发数字不应写成硬门槛。 |
| REL-19 | 发布/批处理不能意外耗尽配额 | **采用** | C-02 是直接反例。执行前核对实际套餐、调用量与发布路径，批量工作不要经昂贵的受限 API 反复转发。 |
| REL-20 | 长批处理有 checkpoint、恢复和停止条件 | **修改后采用** | 对耗时或重做成本高的批处理有必要；短任务不必建 checkpoint。恢复逻辑应先建立退出观测，再决定自动续跑。 |
| REL-21 | 备份/灾备/回滚产物需要真实恢复演练 | **修改后采用** | 高价值数据需要验证恢复；频率与演练规模按业务损失风险决定。仅看到备份文件不算可恢复。 |
| REL-22 | 依赖故障时明确降级行为 | **修改后采用** | 关键依赖要说明 fail-open、fail-closed 或降级的选择依据；不是每个依赖都需要复杂熔断器。 |
| REL-23 | 关键资源有容量边界与监控 | **采用** | Worker CPU、内存、子请求和账户额度都可能是硬限制。应核对实际平台并设置合理保护，不能只等资源打满才发现。 |
| REL-24 | 复现次数不是可靠性指标，要验证根因消失 | **采用** | B-02 直接对应。连续刷新几次没崩只证明该次没崩，不能证明 N+1、请求放大和资源累积已解决。 |
| REL-25 | 保护机制也要验正常路径与恢复路径 | **采用** | D-01/D-02/G-01～G-03 说明锁和权限保护可能导致系统不可用。必须验证合法操作、冲突后的恢复与无关任务不受影响。 |

## 第一版结论

优先正式化：**唯一发布责任、可追溯产物、发布后真实验收、平台资源边界、有限重试、恢复能力和可行动的观测。** Canary、Kubernetes probes、熔断器等依平台与风险按需采用，不强加给所有项目。
