# MySQL / 关系数据库：逐条评估

> 对应来源：../references/mysql.md。主要案例：A-04、A-05、A-08～A-10、B-03、C-02。
> **适用边界：** MySQL 专有项只适用于 MySQL；通用关系数据库原则可用于 D1/SQLite/PostgreSQL，但必须核对对应数据库的语法、事务和执行计划能力。当前项目使用 D1 的地方，不应照抄 MySQL 专有实现。

| ID | 候选原则 | 第一版结论 | 评估理由与边界 |
| --- | --- | --- | --- |
| MYSQL-01 | 事务业务表优先 InnoDB | **按需采用** | 只适用于 MySQL。新 MySQL 业务通常以 InnoDB 为默认，但不能把它写成所有后端项目规则；D1/SQLite 等由平台引擎决定。 |
| MYSQL-02 | 核心表显式定义主键 | **采用** | 稳定主键有利于关联、更新、审计和迁移。临时 staging 表是否需要业务主键可按用途决定，但核心持久表不能依赖隐式 rowid。 |
| MYSQL-03 | InnoDB 主键短且稳定 | **修改后采用** | 对 InnoDB 聚簇索引有实际意义；通用规则是 ID 应稳定、索引成本可控，不要求所有数据库都使用整数 ID，也不禁止有业务意义的自然键。 |
| MYSQL-04 | 数据类型匹配真实语义 | **采用** | 可避免精度损失、溢出、无谓存储和模糊语义。先明确单位、精度、时区、可空含义，再选类型。 |
| MYSQL-05 | 必填字段用 NOT NULL，NULL 不承载多个含义 | **采用** | 数据边界应在 Schema 中表达。只有未知/未提供/不适用确实是合法状态时才允许 NULL，不能把 NULL 一律当 0 或空字符串。 |
| MYSQL-06 | 业务唯一性有可执行约束 | **采用** | 并发请求、重试和重复导入都可能造成竞态，应用层先查再写不能保证唯一。优先使用唯一约束或原子写入。 |
| MYSQL-07 | 索引围绕真实查询设计 | **采用** | 不机械给每列建索引；结合真实 WHERE、JOIN、ORDER BY 和数据规模验证。索引既可能加速读，也会拖慢写入。 |
| MYSQL-08 | 复合索引按真实访问模式设计 | **采用** | 列顺序取决于过滤与排序组合，不能只按字段出现顺序猜。对关键查询用执行计划验证。 |
| MYSQL-09 | 索引成本包含写放大、存储和缓存 | **采用** | 索引不是免费优化；只有真实读取收益足以覆盖写入和维护成本时才保留。 |
| MYSQL-10 | 重要/慢查询查看执行计划 | **修改后采用** | 对慢查询、热点路径、复杂 JOIN 和性能回归必须看执行计划；不要求每个简单查询都附 EXPLAIN 证据。 |
| MYSQL-11 | 大表避免无理由全表扫描 | **修改后采用** | 全表扫描不是天然错误：小表、低选择性查询或一次性分析可能更合理。要求对真实数据量和调用频率判断成本，不是禁止全表扫描。 |
| MYSQL-12 | 增长型集合查询必须有边界 | **采用** | A-04 和 B-03 已证明全量读取与 N+1 会在普通使用中放大。边界可以是分页、硬上限或被证明永远很小的集合，不能默认无限增长。 |
| MYSQL-13 | 大数据量深分页评估 keyset pagination | **按需采用** | 对大表、深分页、稳定排序场景有价值；小型管理页或必须跳到任意页时 OFFSET 可能更简单。不要机械替换所有分页。 |
| MYSQL-14 | 事务只覆盖必要的一致性操作 | **采用** | 长事务会扩大锁持有时间和冲突概率。事务应围绕业务不变量，而不是整个 HTTP 请求生命周期。 |
| MYSQL-15 | 事务中不等待外部 HTTP、上传或人工操作 | **采用** | 外部延迟不可控，可能长期占锁并降低吞吐。先准备数据，事务内只做必要的原子读写。 |
| MYSQL-16 | 多行/多表更新尽量保持一致访问顺序 | **修改后采用** | 有助于降低死锁，但不能保证没有死锁。对有竞争的事务路径有价值，不必写成每个 SQL 的形式化规则。 |
| MYSQL-17 | 将死锁视为可发生，并安全重试 | **采用** | 关系数据库并发运行中死锁无法靠愿望消除。重试必须重放完整事务，且不能重复触发外部副作用。 |
| MYSQL-18 | 避免长时间 idle in transaction | **不采用** | 该术语主要用于 PostgreSQL 语境，不应伪装成通用 MySQL 军规。替代原则是避免长时间打开事务、持锁或持有快照，并按具体数据库引擎实现检查。 |
| MYSQL-19 | 批量写入优先批处理而非大量单行往返 | **修改后采用** | 大批量导入通常收益明确，适合 Importer；小型在线事务仍以正确性和简单性优先。需要同时考虑单批大小、锁、限额和失败恢复。 |
| MYSQL-20 | 不要先读数千行再在应用层截断 | **采用** | A-04/B-03 直接对应。限制 SQL 返回和处理的规模，而不是仅在响应前切片；同时检查数据库调用次数。 |
| MYSQL-21 | 数据库约束、应用校验、业务模型各司其职 | **采用** | Schema 约束兜底数据完整性，应用层提供可理解的错误，业务模型负责规则。任何单层都不应独自承担所有职责。 |
| MYSQL-22 | 外键按项目边界决定；拒绝外键需替代一致性检查 | **修改后采用** | 不把所有项目都必须外键或外键都不好作为通用规则。Golf 已明确同一数据颜色内允许外键、跨颜色禁止；这是该项目的硬边界，其他项目按数据所有权制定。 |
| MYSQL-23 | Schema migration 可审计、可重放，并考虑新旧代码共存 | **采用** | 自动发布和多环境需要可重复迁移；迁移顺序应考虑部署窗口、回滚和新旧代码兼容，不能靠手工改线上库。 |
| MYSQL-24 | 备份要验证恢复并定义恢复目标 | **修改后采用** | 生产数据需要恢复演练，但 RPO/RTO 和演练频率应按业务重要性决定。小型低风险项目不必复制大型企业灾备流程。 |
| MYSQL-25 | 性能优化基于实测慢点和真实基线 | **采用** | B-05 是直接反例。不要先编造固定行数/毫秒阈值；先用平台限制、用户要求、查询计划或真实 profiling 形成门槛。 |

## 第一版结论

数据库领域适合进入正式 Contract 的核心原则是：**数据完整性可执行、增长型查询有界、事务边界清楚、性能判断有真实证据、原始数据与业务写入按所有权隔离。** MySQL 专有优化留在对应数据库的实现指南，不强制所有项目统一数据库技术。
