## 评审状态

- **采用**：建议作为跨项目默认原则，仍需在正式 Contract 中定义适用范围与验收方式。
- **修改后采用**：原则有效，但原始表述太绝对，或必须结合项目约束调整。
- **按需采用**：只有满足明确条件时才采用，不能成为所有项目的默认机制。
- **不采用**：不接受原规则作为通用要求；文档中说明原因，必要时给出替代原则。

这些状态是本版评估结论，不等于已经写进正式 Contract，也不代表每条都需要新增程序检查。

## 评估依据

每条候选规则综合考虑：

1. **真实案例**：见 ../real-cases/counterexamples.md。案例用于追溯事实，不把所有案例都硬归到后端。
2. **业界实践**：见 ../references/ 对应领域文件，优先标准、官方文档和成熟工程指南。
3. **我们的现实**：独立开发者主导、多仓项目、前后端分离、Cloudflare Worker / D1 / R2、发布额度有限、要求可观察和独立验收；不同项目可能采用不同数据库与运行平台。
4. **当前技术演进**：优先 API 契约机器可读、OpenTelemetry 等通用观测语义、托管/Serverless 原生能力、模块化单体与按需拆分、对象存储直传直下；不把微服务、消息队列、缓存、Service Mesh 或复杂编排视为现代化的必选项。
5. **实施成本与误伤风险**：规则能否解决真实问题、能否被机器可靠检查、是否会增加不必要的锁/流程/基础设施。

## 边界

- 一条行业实践可能正确，但不适合所有项目。要明确适用条件，而不是简单照抄。
- “采用”不等于“每条都写一个 lint”；可能由测试、部署约束、监控、语义 Review 或操作习惯承载。
- 不因某个案例发生过，就默认必须增加新机制；先检查能否通过删除错误实现、复用已有机制或修正边界解决。
- 不为追求数字完整而发明硬性能阈值。数值门槛必须来自平台限制、用户要求、SLO 或实测基线。
- 对现状不确定的案例标注待核实，不把对话中的风险描述升级成已审计的代码事实。
- 每个领域先完成初步评估，再由用户逐条确认；确认后才从 Draft 提炼正式 Contract。

## 第一版范围

本版逐条评估 references/ 中 **229 条候选实践**，覆盖 11 个领域。重点不是追求规则数量，而是找出能跨项目复用、能降低真实故障概率、又不会把工程变得更复杂的最小集合。
