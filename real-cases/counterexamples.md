# 反例总表（Draft）

> 这是 `backend.contract` 的证据池，不是正式规范。先保留真实问题，再决定哪些值得变成静态检查、测试、CI、运行时约束或 Review 条件。
> 标记：**已记录**＝已有 me.super / 项目材料；**对话事实**＝近期对话中明确出现；**待核实**＝方向已确认，但当前实现仍需再查。

## A. 架构、API、数据边界

### A-01｜前后端分离被做成 JS 再转发后端 API
**已记录，原 N-013。** Golf 的目标是后端提供 API、浏览器直接访问；实际却加了没有真实职责依据的 JS 转发层。目录拆开和单测通过都不能证明调用拓扑正确，必须看浏览器真实请求路径。

### A-02｜纯静态资源进入 Worker
**已记录 / 对话事实。** Golf 发布后静态资源仍经过 Cloudflare Worker。迁移 Python/Pyodide 后，同一页面更容易触及资源限制。静态资源没有业务理由消耗后端计算运行时。

### A-03｜页面首屏二十多个请求，且加载无关用户和无关数据
**已记录，原 N-016。** 深链接先加载默认学员，再加载目标学员；列表后继续逐 session 查 overview，TrackMan / Biomeca 追加查询。页面需求、API 形状、后端查询拓扑没有一起设计，形成请求放大。

### A-04｜列表接口无分页、无硬上限
**已记录，原 N-017。** edits、source artifacts 等增长型集合存在全量查询。当前数据少不是设计边界；Review 应看分页、默认 limit、硬上限和数据库真实读取范围。

### A-05｜API 只暴露原始资源，汇总计算被推给前端
**已记录，原 N-018。** 前端重复筛 sessions / shots、统计、分组、计算 summary。RESTful 资源拆分不等于读模型合理；稳定、高频汇总应由服务端提供合适的 aggregate / read model，必要时允许有意识的数据冗余。

### A-06｜Importer 为内部导入专门绕一层 API
**对话事实。** 数据导入程序本来可以直接持久化，却一度考虑通过 API 写入。没有外部消费者需求时，这只是多一层故障面。API 不应成为内部数据管道的仪式性中转层。

### A-07｜API / Internal / Pipeline 职责互相渗透
**已记录。** Golf 后端后来专门加门禁：API 不直接依赖 pipeline/parser/derived，Internal 不反向依赖 API。这个门禁对应的真实反例是“HTTP 层”和“导入/计算实现”容易揉在一起。

### A-08｜设备原始数据与用户/教练数据边界不清
**待核实。** 最近 Golf 数据治理已明确：治理后人工数据必须与设备导出数据彻底分离，避免重导覆盖人工内容、source of truth 混乱。当前究竟哪些表已经混写，需以后按最新表关系图核实。

### A-09｜原始备份、产品对象、发布对象混成一个存储语义
**对话事实。** R2 曾倾向用泛化 artifacts 思路承载不同生命周期数据。用户明确要求原始备份与产品对象隔离，普通发布不能删除备份，也不能把原始包变成产品下载路径。

### A-10｜NAS / 原始包被当成日常在线工作集
**对话事实。** Treasure、Golf 都出现过任务反复访问 NAS 或原始包导致卡顿。冷源、备份源应该用于恢复或导入，不应偷偷成为正常运行依赖。

### A-11｜Schema 设计依赖 Owner 发现关键语义与消费缺口
**对话事实（2026-11-26，三叶阅读）。** 用户连续指出消歧模型与词典选择目标未对齐、原词典主次关系丢失、编译各层应可独立被 Reader 使用等设计问题。具体实现现状不由此推断。共性教训：不能只凭 Schema 文档自洽或结构校验判断设计成立，应在设计时用真实来源样本、实际消费路径及反例挑战其表达能力，区分设计缺陷与转换/消费实现错误。Owner 不应替 Agent 承担技术缺口发现工作。

## B. 性能与生产可靠性

### B-01｜迁移 Python 后，同一页面从正常变成 Cloudflare 1102
**对话事实。** 功能迁移后没有同时重新核对运行时开销、重复解析、路由范围、请求扇出与查询复杂度。技术栈替换不能只做功能等价验收。

### B-02｜单用户普通刷新几次即可把 Worker 打满
**已记录，原 N-016。** 这不是压测。更不能把“刷新 3 次/4 次不崩”当验收标准；刷新次数只是复现手段，验收应证明请求放大、N+1、无关加载和资源累积的根因已消失。

### B-03｜N+1 藏在一个“列表 API”背后
**已记录，原 N-016。** 一个 HTTP 请求内部仍可能逐条 session 串行查数据库/对象存储。只数 HTTP 请求个数会漏掉真正的复杂度。

### B-04｜输入字节有界，被误判成整回任务可持续
**已记录，原 N-010。** Treasure 小说 Review 因模型视图从数 MB 降到约 429 KB 就判断“可运行”，但仍需一次处理上百对象，checkpoint 与恢复不足。可持续性必须同时看工作对象数、运行时间、中断恢复和失败重做成本。

### B-05｜没有基线却发明性能硬阈值
**已记录，原 N-011。** Task 中按“性能、验收”等关键词写入合成规模和数字门槛，却没有用户要求、平台硬限制或实测基线。没有来源的数字不是工程约束。

## C. 发布、部署、观测

### C-01｜同一提交由两套 CI / 发布链重复触发
**对话事实。** Workspace CI 与 Importer CI 曾对同一提交组合重复部署。concurrency 能串行或 cancel，不等于真正去重；发布责任应该唯一。

### C-02｜发布实现本身瞬间耗尽请求额度
**对话事实。** 曾出现一次发布很快耗尽当天请求额度。批量上传、全量遍历等不应通过受限 Worker HTTP 路径完成；发布工具自己的请求成本也是系统成本。

### C-03｜/health 200 被当成系统健康
**对话事实。** 健康端点正常并不能证明登录、训练深链接、图表、R2/D1 或 Worker CPU 正常。进程存活与用户任务可完成是两个层级。

### C-04｜已有平台日志，却先说“没有日志”
**已记录，原 N-016。** CPU 超限排障中，后来才查看平台日志并找到 Worker exceeded CPU time limit。排障应先查已有平台日志、应用日志、trace，再下结论“证据缺失”。

### C-05｜应用日志没写完，被误读成“没有错误”
**已记录，原 N-016。** 平台直接终止 Worker 时，应用层可能来不及完成日志。没有应用错误记录不能推导请求没失败，必须区分平台终止、应用异常、客户端错误和日志链路中断。

### C-06｜静态路由修复通过，但真实认证链路仍未验证
**对话事实。** 某次本地 invocation / 定向测试已绿，但隔离 D1 缺 schema，真实认证浏览器验收一度无法完成。局部验证不能升级成“发布完成”。

## D. 状态、工具与执行控制面

### D-01｜Owner 写保护把正常工作也锁死
**已记录，原 N-015。** Butler 曾把“Owner 对执行 Agent 只读”做成硬保护，结果正常 Owner 更新也被拒绝。问题不是保护不够聪明，而是没有先确认真正要保护的业务不变量。

### D-02｜未知旧 Codex 会话 / 锁阻塞新任务
**对话事实。** 系统知道“可能有旧 session”，却不能清楚回答谁持有、是否仍活着、为什么没释放、怎么恢复。只会拒绝、不会恢复的锁，会把理论风险变成确定故障。

### D-03｜Agent 已启动，但用户看不到 TUI
**对话事实。** Butler 新版曾出现用户无法看到 TUI，导致授权和真实状态不可见。后续已明确默认 Codex TUI 可见、GUI 可接上同一会话。可见、可接管、可授权属于长任务可靠性。

### D-04｜Agent 提前结束，但系统解释不了为什么
**对话事实。** Agent 留下中途日志后直接结束。当前首先缺的不是自动续跑，而是退出原因可观测性；未知原因下自动恢复只会把故障循环化。

### D-05｜源码 / 测试有工具，真实生产连接却没有
**对话事实。** `update_task` 曾在源码和测试中存在，但当前真实工具目录没有暴露。实现仓状态不等于发布控制面状态；必须从真实消费者入口验收。

### D-06｜扫描快照被当成实时项目状态
**对话事实。** 项目扫描后 Git 已变化，但摘要仍把旧状态当现在。任何缓存/扫描都必须带时间与新鲜度语义，“上次看到”不能等于“当前事实”。

### D-07｜工具自动测试通过，但从未做真实生产调用
**对话事实。** `prepare_task` 等能力一度只有类型检查 / 测试，没有生产会话完整调用证据。工具系统必须验连接、权限、返回、状态衔接和下游消费。

### D-08｜ChatGPT 开 Task，最后却自己直接实现
**对话事实。** 期望闭环是“ChatGPT 设计 → Agent 实施 → ChatGPT 验收”，实际多次退化成 Agent 没跑通后 ChatGPT 直接改代码。这样无法证明 Agent 工作流本身真的可用。

## E. Task、Review 与协作

### E-01｜只汇报，不主动推进
**已记录，原 N-001。** 明明权限内可以继续修复、验收和收尾，却反复只报告状态，用户被迫成为监工。

### E-02｜显而易见的小问题被升级成实验和新机制
**已记录，原 N-002。** 小 bug 不直接修，先设计实验、审计、状态层、协议。只有真实不确定性才值得实验。

### E-03｜Task 没按执行者设计，用户被迫频繁重启
**已记录，原 N-003。** 没考虑模型能力、执行界面、可续跑性、一次窗口和人工调度成本。Task 不是越细越好，而是应推进到一个有意义完成点。

### E-04｜已有 Owner / 接管说明，却没先读就开始设计
**已记录，原 N-004、N-011。** 能复述“先查 Owner、实现、历史”，真实任务仍按关键词拼方案。规则会背不代表行为受约束。

### E-05｜无视已有控制面，又提一套重复系统
**已记录，原 N-005。** 没先盘点 Rounds / Ledger / Butler / me.super 已有职责，就提新的 Runtime Protocol / 状态层。新增系统前必须先证明现有能力确实有缺口。

### E-06｜“开 Task”退化成生成一段 Prompt
**已记录，原 N-006。** 没结合当前阶段、资产、执行者边界、禁止项、验收条件，只让低模型“去读规则然后做”。Task 是项目推进决策，不是 Prompt 模板。

### E-07｜为了兼容少量旧资产，连续投入高成本
**已记录，原 N-007。** Treasure 旧资产很少，却连续做兼容 prototype / proof / migration；最终继续兼容的成本高于直接重做。沉没成本低时应该主动比较重做方案。

### E-08｜大型重构先跑 TUI，之后才检查额度与授权
**已记录，原 N-008。** 执行界面、额度、授权、可接管性应该在大型任务启动前决定，而不是启动后才发现资源不足。

### E-09｜只读 Human Feedback 被做成正式语义提交的阻塞条件
**已记录，原 N-009。** Markdown / 图片呈现问题反过来阻塞已经完成的语义结果。呈现层失败不应撤销业务事实。

### E-10｜用数据库行数 / 空 pending 队列证明“36/36 完成”
**已记录，原 N-009。** 状态数量只证明状态，不证明结果有正确语义来源、模型执行证据或质量。

### E-11｜Task 尚未执行，Progress / Result 已经写得像做完了
**对话事实。** 后续 Agent 会把这些预填内容当既有事实，从“剩余缺口”继续跑。计划、预期结果、执行事实必须分开；未执行不能预填完成状态。

### E-12｜先读执行者结论，再声称“独立验收”
**对话事实。** Review 若先读 Progress / Result / Agent 自报，就已经被执行者框定。近期 Butler 两阶段 Review 正是在修这个问题：先由 Intent + Owner 独立推导可观察标准，再看 evidence。

### E-13｜“任务结束”被写成“任务验收通过”
**对话事实。** Agent 进程结束、Task completed、commit 存在都不等于 accepted。执行完成与验收通过必须是两个事实。

## F. 常识、Sanity Check 与最终产品结果

### F-01｜理论上还有不确定性，就继续研究
**已记录，原 N-012。** Golf 多次出现现实解释已经很强，却因为理论上还可能有别的情况继续深挖。继续研究前应先问：A/B 不同答案会不会改变实际决策？

### F-02｜单位解释已经产生不可能的人体/物理结果，仍继续考证单位
**已记录，原 N-012。** 常识本身就是证据。明显不可能的解释应该先排除，而不是再花高模型额度做考古。

### F-03｜双机位只差肉眼不可感知的几帧，仍深挖同步身份
**已记录，原 N-012。** 如果查清具体来源也不会改变产品实现和体验，就没有继续研究的价值。

### F-04｜历史变化显示几百个百分点，数学可能对但产品表达荒谬
**已记录，原 N-012。** 低基数直接算百分比可能公式没错，却严重误导用户。产品结果本身是否合理也是验收对象。

### F-05｜产物很完整、很漂亮，但没解决真实问题
**跨域类比，原 N-014。** 厨房收纳图看起来完整，却违反真实空间、设备功能和卫生常识。它与工程里“测试全绿、架构图漂亮、真实用户路径明显错误”是同一种失败：局部产物质量不能替代整体目标正确。

### F-06｜把“规则写进文档”当成问题已经解决
**已记录，原 N-011 等。** 补 Owner / AGENTS / Review 规则不能证明行为改善。只有后续真实任务在用户提醒前做对，才算经验生效。

## G. 保护机制与过度治理

### G-01｜为了防错误不断加锁，最后正常路径也不能工作
**已记录，原 N-015。** Butler、Treasure、Golf 都出现过“更严格 = 更可靠”的倾向。锁、权限、阶段门槛本身会带来误阻断、残留状态、死锁和恢复成本。

### G-02｜局部风险被扩大成全局阻塞
**已记录，原 N-015。** 一个局部文件、阶段或写者冲突，不应阻塞无关任务。保护范围必须与风险范围一致。

### G-03｜用新增治理机制修复“过度治理”
**已记录，原 N-015。** 发现锁太多之后再加“锁治理流程”会继续复发。优先删除、缩小、简化已有机制，而不是再包一层。

## H. 仍需继续核实的条目

1. **Golf 哪些设备表真实存在用户/教练写入字段。** 目标边界已定，但当前实现要按最新关系图核实。
2. **哪些 API 仍存在“先全量读取再内存截断”的伪分页。** 已确认部分无界，不代表全部都一样。
3. **哪些汇总应物化成表、哪些只需要 SQL / 服务端即时聚合。** 必须由真实页面需求、更新频率和成本决定，不能机械建汇总表。
4. **Python Worker 超限的成本占比。** 已确认请求放大与 CPU 超限，但 Pyodide、SQL、R2/D1、序列化各占多少仍需 tracing / profiling。
5. **Butler Agent 提前结束的真实退出原因。** 目前能确认“不可观测”本身是问题，不能猜具体退出类型。

## I. 从反例抽象 Contract 时要避免的二次错误

- 不要把每条反例机械变成一个 lint。
- 不要默认“更严格 = 更正确”。
- 不要因为静态检查能过，就忽略真实浏览器、API、数据库、Worker 行为。
- 不要用没有基线的固定数字代替真实性能要求。
- 不要把所有列表机械分页，也不要把所有汇总机械物化。
- 不要为了防 Agent 犯错，再造一个比业务系统更复杂的控制系统。
- 优先找少量能跨项目复用、又能直接阻断真实事故的约束。
